# Gate 1 delta — §12.14 System log bot

Spec under review: the TASK-030 sa brief (section text to be appended as §12.14 of docs/specs/2026-11-23-phase1-spec-s12-discord-rollout.md). Code read for evidence: `core/functions/logs/logsystem.py` (`Log._render`, `Log.write_log`, `MaskingHandler`), `core/functions/logs/masking.py`, `core/discord/allowlist.py` (`Gate.channel_ok`, `Gate.allowed_channel`), `core/discord/notifier.py`, `core/discord/client.py` (`_admin_line`, `_common_ready`, `_intake_ready`), `core/discord/sinks.py`, `core/discord/threads.py`, `core/config.py` (`_check_discord`, `_secret_values`, `Config.__repr__`), `core/budget/guard.py` (`_notice`).

Owner decisions taken as given: System optional until the app exists; Praw seeing #bot-log is a WARNING, not a refusal; #bot-log View limited to the human approver role (all 3 humans); no pings on ERROR/CRITICAL; `/budget` refused in #bot-log.

## Verdict
**CONDITIONAL_APPROVE.** The design is sound. It forwards only post-`_render` lines, so mask_obj and the exact-value check have already run. It masks the text again before sending, posts with `AllowedMentions.none()` inside a code block with backticks replaced, and blocks feedback loops (`lib.log`/`logforward` are skipped and `offer` never logs). It never falls back to Praw, keeps the System token out of `repr`, and grants System only View+Send on one channel. Backend must implement S1214-01..05 before merge. S1214-06 is a docs/ops step before System goes live.

## Findings

### S1214-01 (Medium, merge) — #bot-log exclusion is inbound-only
12.14.5 adds the exclusion only to `Gate.allowed_channel` and leaves `channel_ok` unchanged so that S12-02 still passes. Every other path that relies on `channel_ok` still accepts #bot-log and its threads:
- `DiscordSinkFactory.for_channel` (`if obj is None or not self.app.gate.channel_ok(obj):  # S12-01`), reached from `reply_gate`, `approvals/service.py` (`sinks.for_channel(chan, persona)`), `client.py` and `threads.py`
- `threads.create_thread` (`or not app.gate.channel_ok(ch)`)
- `embeds.py` (approval embed), `approver.py`, `voice/session.py` and `pulluser/service.py`

`threads.history`/`_channel` has no allowlist check at all. Only `for_target` refuses #bot-log. As written, D3's code-side promise that Praw does not post in #bot-log rests on Discord permissions alone (rule 8: restricting a channel means checking every write to it).

Required:
1. One predicate, `Gate.excluded(ch)`, true when `cfg.admin_notify_channel_id in (ch.id, ch.parent_id)`. `channel_ok` returns False when it is true, so every caller above inherits it. This also covers full mode with an empty allowlist.
2. Amend S12-02 in the spec and in `_intake_ready`: the admin channel must exist (`channel_not_found`) but is no longer checked with `channel_ok`. The tasks and approval channels keep the full check.
3. Before relying on `channel_not_found` for the admin channel, verify with a fake or a live probe that `g.get_channel` still returns a channel the intake bot cannot View. If it does not, removing Praw's View would cause a fatal startup refusal. In that case drop the admin channel from the S12-02 loop entirely; System's own check in 12.14.3 step 4 covers it.
4. Tests: `for_channel(#bot-log)`, `for_channel(thread whose parent is #bot-log)` and `create_thread` in #bot-log each raise `target_not_allowed`, in both coexist and full-with-empty-allowlist mode.

Rule 3 re-check of the widened refusal: Praw's only remaining writes to #bot-log were admin lines, budget notices and the scan alert, and all three move to System. `/budget` in #bot-log is refused, which the owner accepted. Approvals live in `APPROVAL_CHANNEL_ID` and are unaffected unless the channels coincide (S1214-04).

### S1214-02 (Medium, merge) — forwarded fields use a denylist
`DROP_KEYS` is a denylist on a new egress path to a third party (rule 6: structural guarantees are allowlists). Any key added later, or a free-text field such as `approval.denied reason=` or `by=`, would be forwarded.

Required: forward only keys in `FORWARD_KEYS = {"error","reason","code","status","persona","agent","id","run","session","user","by","count","guild","kind","level","size","exc_type","model","provider","task","event","on_deleted"}`. This is the set used in today's WARNING+ calls under `core/`; extend it only through spec edits. Drop unknown keys silently. Keep scalar-only, VALUE_MAX and `\n`/`\r` folding. `DROP_KEYS` may remain as a second layer.

Test: a WARNING record with `note="free text"` and `prompt="x"` posts neither key nor value.

### S1214-03 (Medium, merge) — lock discipline (deadlock and loop blocking)
`offer` holds a `threading.Lock`. The sender logs `logforward.send_failed`, and `_system_failed` logs `system.disabled` and clears the queue. If either logs while holding that lock, `write_log → tap → offer` blocks on the same non-reentrant lock and the event loop hangs.

Required:
1. `write_log` calls the tap after leaving `Log._lock`.
2. `offer` runs `json.loads` and the skip filters before taking the forwarder lock.
3. The forwarder lock guards only deque/dict operations. Never call `write_log` or `await` while holding it, including in the sender drain, `_system_failed` and `shutdown`.
4. Read the tap once into a local variable.

Test: a fake channel whose `send` raises Forbidden, run while a worker thread calls `offer` in a loop. Assert that `logforward.stopped` is reached within a timeout.

### S1214-04 (Low, merge) — channel coincidence and type
If `ADMIN_NOTIFY_CHANNEL_ID` equals `APPROVAL_CHANNEL_ID` or `TASKS_CHANNEL_ID`, the S1214-01 exclusion silently disables approvals or tasks.

Required:
- `_check_discord` refuses `admin_channel_shared` when the admin channel id equals either of them.
- `_system_ready` step 4 refuses `channel_not_found` unless the channel is a text channel. A category, forum or voice channel would defeat the `(id, parent_id)` check.

### S1214-05 (Low, merge) — bounds and leak-test shape
- After the final `mask_secrets`, cut content to 2000. Masking can lengthen text, for example `Bearer x` becomes `Bearer ***`.
- Cap the dedup and `suppressed` maps: clear them when they exceed 1000 keys, as `Gate._note` does.
- A2 must assert on the real `content` passed to the fake `ch.send` (rule 16). Plant a configured secret under a non-secret key name and a regex-shaped Discord token, and assert both are absent.
- `_system_ready` also refuses `system_over_privileged` if `p.administrator or p.mention_everyone` (least privilege, fail closed).

### S1214-06 (Low, before System goes live) — channel permissions
Add to docs/helper/discord-apps.md:
- #bot-log denies View to `@everyone`, the persona role and the intake bot role.
- System has no guild-level role permissions beyond the #bot-log overwrite and never has Administrator.
- Guild Administrators can still read #bot-log.
- If `DISCORD_BOT_TOKEN_SYSTEM` leaks, rotate it in the Developer Portal and update the env file.

## Accepted residuals
- `Guard._notice` records `first_notice` before calling the notifier, so a budget notice raised while System is down is lost for that day. It is still logged as `budget.notice_failed` in the file. This is availability only.
- #bot-log shows user, persona and channel ids. Accepted because View is limited to the 3 human members.
- Dedup keyed on `(level, system, event)` hides repeats from Discord. The file log keeps every record.
- A user-influenced string inside an allowed field can forge text within one line. It cannot add new lines (newlines are folded) or mention anyone.
