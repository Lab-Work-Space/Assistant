# Security Gate 1: WS-1

Verdict: **APPROVED WITH CONDITIONS**. Conditions WS-C1 to WS-C24 bind WS-P1, WS-BE1..BE3, the tester (WS-T1/T2), devops (WS-DEP) and Gate 2 (WS-S2). The owner decisions are taken as given: a zip goes to Discord, `ws_run` reaches only the registry, and the work starts now. This gate bounds those decisions; it does not reopen them. "Brief" means the SA brief, cited by its own section numbers. Code citations use a content anchor first; line numbers are hints only.

What the design gets right:
- **Commands.** The model never builds argv. It picks one verb from a fixed set (brief 5.3), and spawn takes an array with no shell.
- **Container and registry.** Each run gets a fresh container with read-only root, `--cap-drop=ALL`, no-new-privileges and limits. Its only network is `none` or an internal network that reaches a GET/HEAD-only registry proxy (`pathAllowed`, "only GET and HEAD are allowed", Authorization dropped). Install runs with `--ignore-scripts --userconfig /dev/null --globalconfig /dev/null --replace-registry-host=always`. That rewrites lockfile `resolved` hosts to the proxy, so a lockfile URL to another host cannot be fetched.
- **Host file access.** It reuses the no-follow chain in tools/plugins/workspace/sandbox.ts: `walk` ("O_RDONLY | C.O_DIRECTORY | C.O_NOFOLLOW"), `checkFile` ("hard-linked files are refused"), `recheck` (dev/ino), and writes through a temp file opened with O_EXCL|O_NOFOLLOW. Probe P2 proved the container can plant a real symlink on the host, so this matters.
- **Approvals.** `NO_APPROVAL_TOOLS` is checked by name inside `approvalFor`. Its existing consumers keep the ws names out of skills (`skillToolAllowed`, "!isNoApproval(name)") and out of tree grants (`assertTreeGrantScope`, "never asks for approval already").
- **Untrusted output.** `untrustedOutput` on `ws_run`, `ws_read` and `ws_list` makes the registry wrap the output and taint both the run and the task (registry.ts, "G2-04: the task keeps the taint"). After that, every other write tool, GitHub push included, asks for approval.
- **Caps and migration.** The cap claim is a single conditional upsert in one transaction ("WHERE ws_run_counts.used < $3"). Migration 040 follows the 023/024 precedent and keeps the schema limit (`tools.byDept` "max(100)", 93 + 7).
- **Docker Desktop version.** The installed build is 4.99.0, a recent release. A 2025 advisory (CVE-2025-9074, from recall) let containers reach the engine API on the VM subnet without a socket mount. The proof that this build is safe is the WS-C21(c)/(d) probe, not the version number.

OD-1 applies unchanged. The app uid can already reach the Docker socket (launcher.ts header: "This is damage limitation, not a boundary"). The argv builder therefore limits what a correct app does with model input. It is not a boundary against a compromised app, and Gate 2 must not credit it as one.

## Conditions

### Container and Docker (WS-BE2)

**WS-C1. Argv and spawn**
- Argv is exactly brief 5.3 plus `--pull=never` and `--log-driver=none` (or `--log-opt max-size=1m --log-opt max-file=1`), with `--ulimit core=0`. WS-T2 shows that output is still captured.
- The image comes from docker/ws/images.json and must match `^sha256:[0-9a-f]{64}$`.
- Spawn uses an argument array, no shell, and env `{PATH, HOME, DOCKER_HOST?}` only (as `realDocker` in launcher.ts).
- Every docker CLI call has a timeout: `version`, `inspect`, `rm -f`, `ps` and `network inspect`.

**WS-C2. Mount source**
- The mount string is rebuilt at each run from the re-validated WS_REAL plus slug. WS_REAL must match `^/[A-Za-z0-9._/-]{1,200}$` and slug the slug regex, so no comma can reach `--mount`.
- `src` is checked with lstat: a directory, not a symlink, and the same dev/ino as recorded when the lock was taken (brief 5.3).

**WS-C3. Argv tests are allowlists**
- The argv test is a deep-equality test against the full fixed list for every verb.
- Negative tests show that the builder cannot emit:
  - a second `--mount`, or any `-v`, `--volume` or `--volumes-from`;
  - `--privileged`, `--cap-add`, `--device` or `--env-file`;
  - `-e NAME` without `=`;
  - `--network host`, `--pid`, `--ipc`, `--userns` or `--uts`;
  - `--security-opt` other than `no-new-privileges`;
  - a mount of `docker.sock`.
- `--user` is the process uid:gid, and boot refuses uid 0 (C4).

**WS-C4. Compose allowlist for docker-compose.ws.yml (global rule 25)**
- One service, with no `ports`, `env_file`, `secrets`, `volumes`, `extra_hosts`, `network_mode` or `privileged`.
- Hardening is the same as devjob `registryproxy` (user 65534, read_only, cap_drop ALL, no-new-privileges, pids/mem/cpus, `/tmp` tmpfs noexec).
- `ws_prepnet` has `internal: true` and subnet 10.88.80.0/24, which no other compose file uses.
- `UPSTREAM_URL` and `UPSTREAM_ALLOW_HTTP` are absent, or default to empty and `0`.
- A unit test parses the file and asserts all of the above.

### WS_ROOT and host file I/O (WS-BE1)

**WS-C5. WS_ROOT placement**
- Boot refuses (`wsDisabled`, fixed reason) when realpath(WS_ROOT) **equals, or is an ancestor of**, any of:
  - `$HOME`, `~/.config`, `~/.config/assistant`, `~/.config/assistant/media`, `~/.config/assistant/backups`, or the directory that holds `executor.sock`;
  - realpath(cwd) or realpath(`~/.claude`);
  - the resolved Praw `workspaceRoot` (app.ts "DEFAULT_WORKSPACE_DIR = 'data/workspace/praw'", env `prawWorkspaceDir`).
- Boot also refuses when realpath(WS_ROOT) is **inside** realpath(cwd), realpath(`~/.claude`) or the Praw `workspaceRoot`.
- The default `~/.config/assistant/workspaces` passes both rules.
- Every other rule in brief 3.1 stays: owner uid, not a symlink, chmod 0700, the regex, and no `.git` in any ancestor.
- Unit tests cover each refused case, a test that the default passes, and a case where the `HOME` env differs from the real home.

**WS-C6. All host I/O goes through the no-follow helpers**
- Every host-side open in ws (read, write, list, delete, export, package.json read, `node` file and tsc file checks) uses `openInWorkspace` or a `ProjectFiles` walk with lstat-only `opendir`, so no call follows a symlink.
- Required tests:
  - Symlinks planted by a container at the leaf, in a parent component and at the root entry are refused on read, write, list, delete and export.
  - A FIFO is refused without blocking.
  - A hard link (nlink 2) is refused.
  - A symlink loop is refused.

**WS-C7. Recursive delete**
- `ws_delete` with `recursive` refuses when any parent component is a symlink.
- Test: delete a directory that holds a symlink to an outside directory with a canary file. The canary survives.

**WS-C8. Usage walk**
- `ProjectFiles.usage()` counts regular files at every depth (no depth cut-off). It uses its own `.ws-tmp-` prefix and counts temp-prefixed files toward bytes and files.
- `bytes` and `nm_bytes` are both measured after **every** run, not only after install verbs.
- Tests:
  - 3 000 files at depth 20 make the next write and run refuse with E_QUOTA.
  - 1.2 GiB written to `node_modules` by a `node` run makes the next run refuse.

**WS-C9. Walk budget**
- Every ws walk (usage, list, export) streams with `opendir`.
- Each walk stops at a fixed entry budget (for example 200 000 entries, `node_modules` included) and a fixed time budget (for example 20 s). Hitting either counts as over quota, and the workspace refuses writes and runs until a `ws_delete` brings it back under.
- Test: a fixture of 250 000 empty files gives E_QUOTA. Peak memory during that walk stays below a stated bound.

**WS-C10. Locking**
- Runs and file operations exclude each other per slug (brief 5.2).
- A stuck slug (E_STUCK) keeps its lock until the next boot sweep.
- Test: a `ws_write` and an export started during a run both get E_BUSY.

### Runs, halt, caps (WS-BE2, WS-BE3)

**WS-C11. Global run cap**
- At most 2 `ws_run` containers run at once across all slugs. A third call gets a fixed error, without waiting and before the claim.
- Test: three concurrent runs in three slugs give exactly two spawns.

**WS-C12. Halt**
- The halt flag is set before `killAll` runs.
- `ws_run` re-checks `isHalted()` right after the claim and immediately before spawn. Every spawned name goes into an in-memory set.
- `killAll` removes `label=ws=1` containers whose names start with `ws-`, plus every name in that set.
- Test: a halt injected between claim and spawn leaves zero `ws=1` containers and returns E_HALTED. The slot stays claimed.

**WS-C13. Claims and boot sweep**
- Claims follow brief 5.4, tree then day in one transaction. Test: a day-cap refusal leaves the tree count unchanged (rollback).
- The boot sweep must confirm zero `ws=1` containers before the group registers; otherwise `wsDisabled`. A sweep failure never leaves the group enabled.

**WS-C14. npm prechecks at every install verb**
- At the workspace root, readdir and compare names lowercased: any entry named `.npmrc` (file, directory or symlink) gives E_NPMRC.
- E_SPEC applies to `dependencies`, `devDependencies`, `optionalDependencies`, `peerDependencies` and `overrides` (recursively).
- `ws_write` refuses `.npmrc` at any depth, in any case.
- Tests: `.NPMRC`, a symlink `.npmrc`, an override `git+https://...`, and an alias `npm:x@1`.

### Output and export

**WS-C15. Export**
- (a) Each zip entry name must pass `validateRel(p, {depth:12, relLength:240})`. Failing entries are skipped and counted, and no entry name contains `\` or `:`.
- (b) Export stops at 2 000 entries (E_EXPORT_SIZE) and never needs ZIP64.
- (c) E_EXPORT_SECRET carries no path: fixed text with a count only. Alternatively, `ws_export` is marked untrustedOutput.
- (d) `provenance.record` for an export is always `tainted=true`.
- (e) The target is `ctx.source` (channelId plus threadId), computed in code as in docs/index.ts ("const target = { channelId: ctx.source.channelId"). The input stays `{slug}` only. With no `ctx.source`, the export is refused.
- (f) The literal-secret scan (precedent vps/static.ts `contentProblem`) covers every included file without NUL bytes, whatever its extension.
- Tests: a file named `a\..\x.js` is skipped; the secret error text holds no path; the provenance row is tainted; and a planted literal from the test secret list refuses the export.

**WS-C16. Run output**
- Order: strip ANSI and C0, then `redactText(tail, secrets)`, then cut to 8 000 characters (brief 5.3). The ring buffer holds at most 64 KiB, so stdout is never buffered unbounded.
- `ws_run`, `ws_read` and `ws_list` have `untrustedOutput: true`.
- Tests: a seeded secret split across the 64 KiB boundary does not leak in clear (redact before cutting); and a run that calls `ws_list` sets `tasks.tainted=true`.

**WS-C17. Logs and audit**
- Audit outcomes are exactly the brief 5.7 formats.
- File content, command arguments beyond the verb, container output and docker stderr never reach logs, audit or incidents.
- Test: a grep over a test run's log and audit for a seeded content marker finds nothing.

### Policy and grants (WS-BE3)

**WS-C18. NO_APPROVAL_TOOLS**
- `NO_APPROVAL_TOOLS` is exactly `['diagram_create','ws_create','ws_write','ws_delete','ws_run','ws_export']`, checked by an exact-equality test.
- The rationale goes in a code comment and in the README. `ws_run` already covers write and delete, because a `node` script can rewrite or wipe `/work`, so approval on the file tools adds nothing. The controls are the container, the host no-follow I/O, the quotas, the caps and the global run cap. `ws_export` is the only outward action, and its target is fixed by WS-C15(e).

**WS-C19. DEPT_ONLY**
- `DEPT_ONLY` maps all 7 names to `software`. `effective()` drops them for every other department from the wildcard, byDept, skills and prompt meta.
- Every tool checks the actor in code first (brief 3.2 step 3).
- `wsGroup` is not registered in the admin registry, and `TREE_GRANT_TOOLS` contains no ws name.
- Tests:
  - All departments, plus Praw `*`, plus a stored byDept that grants `ws_run` to marketing: none sees ws tools.
  - A direct call by a marketing head is refused with E_DEPT.
  - A `tool_request` approval naming `ws_run` for another department has no effect.

**WS-C20. Migration 040**
- The SQL is used as written in brief 5.4.
- DB tests cover: a software list of 93 entries (gets 7) and of 94 (unchanged); a `software` key that is absent (unchanged, so it fails closed); a value of `{}`; a non-array value; other departments byte-identical; and up then down restoring the original list.
- The schema still validates the result (`max(100)`).

### Probes and release (WS-T2, WS-DEP, WS-S2)

**WS-C21. P4 before `ws.enabled` can be turned on**
Run P4 against the real stack, with a runner container on `ws_prepnet`. It must show:
- (a) `http://10.88.80.2:4873/react` returns 200;
- (b) a TCP connection to `https://example.com` fails. This part blocks. Also record whether a DNS lookup of an external name resolves, but that result does not block. Only npm runs on this network (`--ignore-scripts`, no project `.npmrc`), so no attacker code is there to use DNS. TCP egress is the boundary;
- (c) `host.docker.internal`, `10.88.80.1`, and `192.168.65.1` / `192.168.65.254` / `192.168.65.7:2375` all fail;
- (d) the same (c) targets fail under `--network none`;
- (e) a lockfile with `resolved: https://example.com/x.tgz` makes `npm ci` fail;
- (f) a POST and a `/-/v1/search` request to the proxy are refused.

Record the evidence in the Gate 2 report.

**WS-C22. P5 symlink probe on the real Docker Desktop**
- From inside a `node` run, symlinks to an absolute host path (a canary file outside WS_ROOT under `$HOME`) and to `../..` cannot read the canary.
- On the host, `ws_read` of each symlink is refused.

**WS-C23. Image scan**
- Gate 2 scans the runner and proxy images (trivy or osv-scanner; neither is installed now, so devops installs one). An unpatched HIGH or CRITICAL fails the gate.
- No new npm dependency is added: zip.ts uses `zlib` only, and package.json is unchanged.

**WS-C24. Release and file list**
- `ws.enabled` is `false` on deploy and is turned on only after Gate 2 APPROVED.
- WS-DEP records `ls -ld` of WS_ROOT (0700, owner) and the images.json ids matching `docker image inspect`.
- Gate 2 ends with the md5 list of every audited file (global rule 2).

## Residual risks (accepted)

- **R1.** A container escape reaches the Docker Desktop VM. That VM sees every shared host folder (by default `/Users`, so `~/.config/assistant/env.local` too). The owner can narrow Desktop file sharing to WS_ROOT and the repo.
- **R2.** A malicious package runs during `npm test`, `npm run` or `node`, without network. It can damage only the workspace.
- **R3.** A model fooled by injected content can write misleading code. Exports and GitHub pushes are reviewed by people.
- **R4.** Workspace files live under the owner's home.
- **R5.** There is no real Chrome test.
- **R6.** One run can fill the host disk within 5 minutes, since quotas are checked only between runs. A refusal below a free-space floor (`statfs`) is recommended but not required.
- **R7.** A race by the owner's own processes stays: Node has no `openat`.
- **R8.** The zip is binary and unmasked. Only the literal-secret scan guards it.
- **R9.** A tainted run can wipe a workspace. The posted zips are its only history.
- **R10.** OD-1: the app uid controls Docker, so the argv builder is not a boundary.
