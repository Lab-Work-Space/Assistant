## Findings

**S11-01 — Medium — §11.11.5 step 6 and the §11.8.3 restore procedure: root follows symlinks in paths the service owns (global rule 17).**
- **Where:** `install -d -o employee -g employee -m 0700 /var/lib/employee /var/lib/employee/knowledge`, `cp -r --update=none …`, `chown -R employee:employee /var/lib/employee/knowledge && chmod -R go-rwx …`, and restore step 2 `install -o employee -g employee -m 0600 <backup> /var/lib/employee/employee.db`.
- **Problem:** the `employee` uid owns `/var/lib/employee`, so it can replace `knowledge` or `employee.db` with a symlink. On the next idempotent `install.sh` run:
  - `install -d` and `chmod -R` follow a symlink given on the command line, so `knowledge -> /etc` chowns or chmods `/etc` (and with `chmod -R`, everything under it);
  - `cp -r` writes into the symlink's target.
  A service-uid compromise therefore becomes root, or host-wide damage, at the next deploy.
- **Required change.** Replace step 6 with:
  ```sh
  install -d -o employee -g employee -m 0700 /var/lib/employee
  runuser -u employee -- sh -c 'umask 077; mkdir -p /var/lib/employee/knowledge && cp -r --update=none /opt/employee/app/knowledge/. /var/lib/employee/knowledge/'
  ```
  Delete the `chown -R` / `chmod -R` line. Replace restore steps 2–3 with:
  ```sh
  runuser -u employee -- sh -c 'umask 077; cp <backup> /var/lib/employee/employee.db.new && rm -f /var/lib/employee/employee.db-wal /var/lib/employee/employee.db-shm && mv -f /var/lib/employee/employee.db.new /var/lib/employee/employee.db'
  ```

**S11-02 — Medium — §11.13 dev account on the prod host.**
- **Problem:**
  - "deploys use sudo" leaves the dev account able to become root.
  - That account runs unhashed `pip install pytest pytest-asyncio` and any coding agent. A cached sudo timestamp turns either into root over prod.
  - Ubuntu's first user is also in `adm`, `lxd` (root-equivalent) and `sudo`. `adm` and `systemd-journal` read the unit's journal.
- **Required change (add to §11.13):**
  - The dev account is in none of `sudo`, `admin`, `lxd`, `docker`, `adm` or `systemd-journal`. Deploys run from a separate admin account, or root over an SSH key.
  - Host check: `id <dev>` lists none of those groups.
  - Test dependencies come from a hashed `constraints/dev.lock` (`pip install --require-hashes -r constraints/dev.lock`).
  - Run the CLI in a subshell so secrets do not stay in the login shell: `(set -a; . ./.env.local; set +a; EMP_CLI_DEV=1 exec .venv/bin/python -m core.cli)`.
  - Edit the env file without editor residue: `sudoedit` with swap, backup and undo files off, or `sudo install -m 0600 /dev/stdin /etc/employee/employee.env`.
  - Step 9 adds `PasswordAuthentication no` and `PermitRootLogin prohibit-password` to sshd.

**S11-03 — Medium — §11.8.1–§11.8.3 backups and erasure.**
- **Problems:**
  1. `pre-migrate-*` files are pruned by count (14), not by age, so expired and erased rows can survive for years. This contradicts §11.8.2 ("at most `BACKUP_KEEP` days").
  2. A restore resurrects expired rows and drops `voice_optouts` rows written after the backup, so a user who opted out could be captured again (PDPA).
  3. The sweep ignores the busy result of `wal_checkpoint(TRUNCATE)`. If the backup holds a read, deleted frames stay in `-wal`.
- **Required change:**
  1. In `backup_to`, after the count prune, also unlink every `daily-*` and `pre-migrate-*` file whose name timestamp is older than `keep` days.
  2. Add restore steps:
     - export `voice_optouts` from the current DB with `sqlite3 -readonly … .dump voice_optouts` (run as employee);
     - after the restore, re-insert those rows with `INSERT OR IGNORE`;
     - run the retention sweep once before starting the service.
  3. The sweep reads row 0 of the `WAL_CHECKPOINT` result and, while it is 1, retries up to 5 times with a 2 s sleep, then logs `wal_checkpoint_busy`.
  4. OQ-3: Hostinger snapshots also capture `knowledge/` (transcripts). The privacy notice must state the snapshot retention.

**S11-04 — Medium — §11.10 and §11.11.5: patch coverage for ffmpeg and the venv (global rule 18).**
- **Problems:**
  - ffmpeg comes from Ubuntu `universe`, and the default `-security` origin does not reliably patch universe packages; many fixes ship only in ESM-apps.
  - The venv is never patched by apt.
  - §11.10 says "`pip-audit` … **or** grype on the venv", but pip-audit cannot see native libraries bundled in wheels (cryptography/OpenSSL, PyNaCl/libsodium).
- **Required change:**
  - Change "or" to "**and**".
  - Gate 2 attaches `apt-cache policy ffmpeg libopus0` and `pro security-status`.
  - When TASK-016 lands, either enable Ubuntu Pro ESM-apps (`pro attach`, `pro enable esm-apps`; it is free for personal use) and add its origin to `51employee-unattended`, or run a weekly grype scan of the host dpkg database.
  - Add a weekly `pip-audit --require-hashes -r constraints/requirements.lock` plus grype on `/opt/employee/venv`.
  - Kernel updates: set `Unattended-Upgrade::Automatic-Reboot "true"` with `Automatic-Reboot-Time "04:30"`, or record that the owner reboots manually when `/var/run/reboot-required` exists.

**S11-05 — Low/Medium — §11.11.5 step 3: deploy integrity.**
- **Problem:** root checks out `<release tag>` and then runs `install.sh` from that tree without verifying it.
- **Required change:** `git -C /opt/employee/app verify-tag <tag>` (signed tags), or check out the commit SHA recorded in the Gate 2 report and refuse a mismatch with `test "$(git rev-parse HEAD)" = "<sha>"`.

**S11-06 — Medium (before enabling the service) — §11.11.2 env-file guard (global rule 7).**
- **Problem:** systemd puts EnvironmentFile values into the process env, so the app cannot tell an `EMP_CLI_DEV` or path line in `employee.env` from the real env. `cli_flag_in_env_file` cannot see it. The grep guard runs only in `install.sh`, so any later `sudoedit` bypasses it.
- **Required change:** add as the first `ExecStartPre` (before migration):
  `ExecStartPre=+/bin/sh -c '! grep -Eq "^[[:space:]]*(export[[:space:]]+)?(EMP_CLI_DEV|DATABASE_PATH|KNOWLEDGE_DIR|LOG_DIR|VOICE_TMP_DIR)[[:space:]]*=" /etc/employee/employee.env'`
  Also reword §11.10: "the service uid cannot open the env file; the values are in the bot's process environ".

**S11-07 — Low — §11.11.4 backup unit hardening gaps.**
- **Problem:** the backup process holds the whole DB in memory but has no core limit or memory cap.
- **Required change:** add these to `employee-backup.service`:
  `LimitCORE=0`, `MemoryMax=512M`, `AmbientCapabilities=`, `LockPersonality=yes`, `RestrictSUIDSGID=yes`, `RestrictRealtime=yes`, `ProtectKernelLogs=yes`, `ProtectClock=yes`, `ProtectHostname=yes`, `ProcSubset=pid`, `RemoveIPC=yes`, `SystemCallErrorNumber=EPERM`.
- **Info:** until a prod DB exists, the timer exits 2 (`db_path_invalid`) every day. Enable the timer only after the first `python -m core.migration`.

**S11-08 — Low — §11.12.3 phase-2 unit details.**
- **Required change.** Replace "the same hardening as §11.11.2" with "the §11.11.2 hardening lines only". The unit has:
  - no `EnvironmentFile=`, no `Environment=` path variables, and no `ReadWritePaths=`;
  - `RestrictAddressFamilies=AF_UNIX` and `IPAddressDeny=any` alongside `PrivateNetwork=yes`.
- `kind.env_secrets` reach an isolated worker only in the stdin JSON preamble, never through the unit's environment.
- `MaxConnections=` is rendered from `JOB_MAX_CONCURRENCY` by `install.sh`, because a unit file cannot read the env file.

**S11-09 — Low — §11.3 `_open_runtime`: SQLite DB config.**
- **Problem:** `fts3_tokenizer('simple')` passes the authorizer (it returned NULL locally on 3.53; the 2-argument form is refused only by compile-time defaults). The target, Ubuntu SQLite 3.45, has different build options.
- **Required change:** before `conn.set_authorizer(_authorizer)`, add:
  `conn.setconfig(sqlite3.SQLITE_DBCONFIG_DEFENSIVE, True)` and `conn.setconfig(sqlite3.SQLITE_DBCONFIG_ENABLE_FTS3_TOKENIZER, False)` (both available in Python 3.12).
  Add T-DB-5 vectors, run on the target host:
  - `SELECT fts3_tokenizer('simple', x'00')`, `VACUUM INTO '/tmp/x.db'`, `SELECT * FROM pragma_table_info('budgets')` and `SELECT load_extension('x')` each raise;
  - `/tmp/x.db` does not exist afterwards.

**S11-10 — Low — §11.11.7 host checks replacing the retired Docker tests (G1-08.6, G2-05).**
- **Required change:**
  - Keep the `git check-ignore` half of `tests/test_container.py`; drop only the image half.
  - Add these host checks:
    - `find /opt/employee -name '.env*'` prints nothing;
    - `find /opt/employee ! -type l -perm /022` prints nothing;
    - `sudo -u <dev> ls /var/lib/employee /var/log/employee` fails;
    - a drop-in with `MemoryMax=1G` makes the service exit with `bounds:MEMORY_MAX`. `_check_memory` returns silently on a read error, so prove it fires under the unit.

**S11-11 — Low — §11.7.6 / §10.7 CLI against the prod DB.**
- **Problem:** `sudo -u employee env EMP_CLI_DEV=1 … python -m core.cli` loads no env file, so it has no token, so `cli_dev_env()` passes. That gives a CLI approver over prod rows.
- **Required change:** `cli_dev_env()` also returns False when `pwd.getpwuid(os.geteuid()).pw_name == "employee"`. Add a test with a monkeypatched `getpwuid`.

## Residuals (accepted, not findings)
- The authorizer is in-process. The only OS boundary for the DB is the uid (§11.4.5).
- Slice A workers share the bot uid (G1-05(b), §11.12.1). They can read the bot's environ, the DB and backups. Optional hardening: `prctl(PR_SET_DUMPABLE, 0)` in the bot hides `/proc/<ppid>/environ` from workers.
- The ffmpeg carve-out (§10.6.4) stays open for TASK-016.
