### 2. Zip reader and validator: PASS

`forge/unzip.ts` `read`:
- **Bombs:** the EOCD is at exactly `length-22` with comment 0, and `cdOff+cdSize === eocd`. Count ≤ 200 and every declared size and the total are checked in the central-directory pass, before any inflate. `inflateRawSync(..., {maxOutputLength: usize})`, then the output length must equal the declared size, then the CRC.
- **Header fields:** version 20/20; flags, time/date, extra, comment, disk, internal and external attributes must all equal what buildZip writes.
- **Local/central:** every local field must equal the central entry, including the name bytes. Entries are contiguous from offset 0, with no gap or overlap.
- **ZIP64:** refused (version 20, sizes over the caps, at most 200 entries).
- **Duplicates:** exact duplicates are refused in the reader. Case collisions are refused in validate P (`toLowerCase` is enough because segments are ASCII only).
- **Traversal:** segments are `^[A-Za-z0-9._-]{1,64}$` and may not start with a dot (so no `.` or `..`); depth ≤ 6; no empty segment; no absolute path. Symlinks cannot be expressed: external attributes must be 0, and the builder writes only regular files.
- **JSON:** a linear depth pre-scan, then a reviver that throws on `__proto__`, `constructor` or `prototype`.
- **package.json:** install scripts and runtime dependency maps are refused.
- **Lockfile:** keys must be `node_modules/...` with `dev:true`, no `hasInstallScript`, and `resolved` from the npm registry.

Note (Info): a lock entry with `link:true` and no `resolved` passes. The lockfile is never shipped and never used at build; WS-1 installs are already arbitrary inside the workspace sandbox.

Note (Info): a file and a directory with the same name (`vendor/a.js` plus `vendor/a.js/b.js`) pass the validator and then fail staging as `stage_dir`. That is availability only.

### 3. Builder: PASS, and each BE3 change is acceptable

- **Argv:** built only in `forge/builder.ts` from constants, the boot-read base id (`BASE_RE`), an integer build id, 64-hex hashes and a regex-checked name (`NAME_RE`). `shell:false` through `realDockerCli`. The golden test covers the exact arrays and the forbidden verbs. `cp` has no `-a` or `-L`.
- **Stage dir:**
  - `verifiedRoot`: lstat, a real directory, uid = euid, `mode & 077 = 0`.
  - `mkdtemp` inside it, then `PATH_RE` and `DIR_RE`.
  - Files are opened `O_CREAT|O_EXCL|O_NOFOLLOW`, then fchmod 0644. Directories are mkdir'ed, then opened `O_DIRECTORY|O_NOFOLLOW`, then chmod 0755.
  - `checkStage` re-walks with lstat (no links, regular files and directories only), checks count and bytes, then re-reads every file with `O_NOFOLLOW` and compares size and sha256 with the manifest (PF-C2).
  - Only a same-uid process could race this, and that is already inside the trust boundary.
- **Hash chain:**
  - `sha256(zip) = b.sha256 = r.sha256`, and the manifest equals the build's and the release's.
  - `validatePlugin` on the pinned bytes gives the same manifest and slug.
  - The staged files match the manifest.
  - The commit label `assistant.forge.sha256` carries the zip sha256, and the int test checks that the saved layer equals the manifest byte for byte.
  - `RELEASE_BOUND` binds `b.image_id = $image`.
- **Config verification:** `verifyImage` compares keys exactly. Only `SET_ON_PURPOSE` keys and `CONFIG_IGNORE` keys may differ. Layers must be the base plus exactly one. The size delta must be ≤ 8 MiB.
- **Cleanup:**
  - The container goes in `finally` (`removeVerified`, verified with `ps`).
  - The stage dir goes in `finally` (`removeStageDir` only removes a `DIR_RE` child of the root).
  - The image goes on every exit other than `staged` (`build` checks `made.id`).
  - A failed removal sets the latch.
  - `recordImage` runs right after the commit; if it fails, the image is removed at once.
- **Sweep:** the `docker ps` name filter is a substring match, but every name is then tested with the anchored `NAME_RE`.
- **BE3 change (a), a 0755 `plugin` child of the 0700 stage dir.** Acceptable. The parent stays private, so no other uid can enter the path. The child is created and then chmod'ed through an `O_NOFOLLOW` handle, and `checkStage` walks the child. The only effect is the mode that `docker cp` stamps on `/srv/plugin` (0755, so uid 65534 can read it).
- **BE3 change (b), `DAEMON_LABELS` = exactly `desktop.docker.io/ports.scheme=v2`.** Acceptable.
  - Only an entry with that exact key and value is deleted before the exact comparison with the three forge labels; any other extra label or value is `verify_failed`.
  - The plugin cannot influence labels: there is no Dockerfile and no container start. `baseAcceptable` requires the base to have no labels.
  - The label means nothing to the R6 runtime, and PF-C10's `assistant.forge` prefix check is unaffected.
- **BE3 change (c), `CONFIG_IGNORE` += `ArgsEscaped`.** Acceptable for Linux. moby and containerd read `ArgsEscaped` only for Windows images. Entrypoint is checked as the exact two-element array and Cmd must be empty, so on Linux it cannot change what runs. The tolerance is wider than needed: it would also accept the new image gaining `ArgsEscaped=true` (G2-FG-10, Info).

### 4. PF-C15 ownership: relax, with an exact condition (no code fix required)

**Decision: PF-C15 is relaxed.** `docker cp` on Docker Desktop keeps the host owner, and the builder cannot chown without starting a container (which would break F1). The accepted condition, binding from now on:
- every entry of the new layer has uid ∈ {0, staging euid} and gid ∈ {0, staging egid};
- the staging euid and egid are never 65534 (the runtime user), so the plugin process never owns its own files;
- the modes are exactly 0644 (files) and 0755 (directories), with no setuid, setgid or sticky bit, no whiteout, no link and no device;
- the runtime keeps `--user 65534:65534`, `--read-only` and `cap-drop ALL`, so no process in the container can chmod, chown or write these files.

Under these conditions, uid 501 and gid 20 give the plugin nothing:
- no process in the container runs as 501;
- group 20 is `dialout` in Alpine, and the runtime user is not a member;
- group and other have no write bit.

`forge/docker.int.test.ts` "PF-C15 probe 3" asserts all of this except the "never 65534" clause. That clause holds on the production host (launchd user uid 501). A one-line builder guard is G2-FG-07 (may follow).

### 5. GC and image removal

- **Candidates (`gcCandidates` plus the `labelled` re-check plus `imageInUse` re-checked right before `rm`):**
  - the image must be a build's kept image (`image_removed_at IS NULL`);
  - the labels must name that build;
  - no pending, active or quarantined server may hold the image id (any slug, any source);
  - and one of: the build failed; or its server has been disabled for more than 7 days; or it has no server 1 h after the build finished.
  - A `building` row is never a candidate. The base has no labels, so it never matches.
- **Orphan pass:** lists `label=assistant.forge=1` images and skips any id a build row keeps. It removes one only when its build label names an existing build with another image id that is not `building`, and rule (c) holds.
  - Gap (**G2-FG-06**, Low): an image the forge did not make can carry those labels, for example a third-party image a Bot Admin added with `/mcp add` as write class (read class is refused by PF-C10). It is removed once its server is disabled or unused.
- **Untagged parent:** `docker image rm <child>` also deletes an untagged parent. I reproduced this on this daemon (Docker 29.9.3, containerd snapshotter) with local images only: a container created from the ws runner and never started, committed twice.
  - Without `--no-prune` the untagged parent was deleted. With `--no-prune` it stayed.
  - The production base is tagged by `build.sh`, and the README says not to untag it. A tag the owner may remove is weaker than a code guarantee.
  - **Fixed (G2-FG-01):** `imageRmArgv` is now `['image','rm','--no-prune',id]`. The golden test, the service int test and the docker int guard are updated, and the real-daemon test passes.
  - A code check of the tag is not needed with `--no-prune`. The base also cannot be a GC target directly: it has no labels, and `BASE_RE` plus the build-row join never yield it.

### 10. Widening the retro queries S7/S8 to `forge_failed`: safe, under conditions

A `forge_failed` row carries no text. Its fields are `dept_id` (taken from `releases.dept_id`), the kind, a code from the closed `BUILD_CODES` list (filtered by S9's `= ANY($1)` and dropped again by `incidentBlock` if unknown), `task_id`, and `ikey` (`forge:<id>`). It is code-built and untainted. Volume is bounded: every build needs a human card, and the caps are 3 per forge, 3 per day and 1 at a time. So a bot cannot flood the S8 trigger.

Conditions:
- S7 and S8 read only `kind`, `code` and the count. Never join `releases.title`, `releases.summary`, the idea text, `plugin_builds` text or any column a bot wrote.
- S7 renders each code through the closed list, the same as `incidentBlock`; an unknown code is dropped.
- The department is `releases.dept_id` (the requester), never the idea's department.
- Know that `stage_*` codes depend on what the plugin does when probed. A bot can choose which closed code appears. That is a few bits from a closed set, not text, and is acceptable.
- Add a test that a `forge_failed` row with an unknown code is not counted by S8 and not shown by S7.

### 12. PF-C23: what the owner must do before turning `forge.enabled` on

The scan was not done; no scanner exists on the host, and pulling one was out of scope. Before switching on:
1. Run `bash docker/forge/build.sh`. Confirm `docker/forge/images.json` holds the printed id, then commit it.
2. Scan `assistant-forge-base:local` with trivy or grype. First prove the scanner with a positive control: an image known to carry a HIGH or CRITICAL finding must be reported. Any unpatched HIGH or CRITICAL in the base means REJECT: do not switch on.
   - The Dockerfile already upgrades zlib (CVE-2026-4738). Check that the scan shows zlib 1.4-r0 or later.
3. Check that npm, npx, corepack and yarn are absent: `command -v npm npx corepack yarn` inside the image prints nothing (README step 2).
4. Restart the service, so `loadBaseId` reads the new file once.
5. Turn `forge.enabled` on. Check #bot-log: there must be no `Plugin forge: the base image is missing or changed` alert. If there is one, `inspectBase` refused the base (labels, volumes, OnBuild, Healthcheck, or a wrong id).
6. Record the scanner name, version, database date and result in this report or a follow-up note. Rescan after every rebuild of the base, at least monthly while forge is on.

**G2-FG-11 analysis.** `requeueStale` runs only when all of these hold:
- `adminCancel` returned `busy`;
- `!this.running`;
- `forge.enabled` is off or unreadable. The switch comes from the DB-backed config, so every process sees the same value.

It then works through the rows `recover()` reads (a read-only SELECT):
- It skips every row that holds an image.
- It re-checks `running` and the switch before each row.
- It calls `requeue(id, interrupted, refund:false)`. Under `FOR UPDATE` this changes only a row that is still `building`.

After that, `adminCancel` is retried.

- **Rows of forges the admin did not name.** Because of the unique index `plugin_builds_one_building ((true)) WHERE status='building'`, at most one `building` row exists globally. Since `adminCancel` answered `busy` for the named forge, that row belongs to the named forge. No other forge's row can be touched.
- **Abuse.** Only a Bot Admin can run it. Each call moves at most one row, and only while the switch is off. A requeued row cannot become `building` again without the switch being on, so repeated cancels cannot burn attempts. No refund is given, the same as the crash recover. At 3 attempts the row becomes `failed:interrupted`, a closed code. No Docker call is made.
- **Race with a real build in this process.** A tick sets `running` before it claims, and claims run only while the switch is on. The per-row re-check prevents losing a build the tick has just claimed. The boot recover runs only while the switch is on. If the switch flips on mid-loop, recover and `requeueStale` serialise on `FOR UPDATE`, and the second call gets `null`.
- **Race with another process, or a build that is still draining after the switch went off.** Nothing enforces a single instance in code; launchd runs one. If a foreign build is still running, it is requeued and then cancelled. Its later `recordImage` (requires `building`), `releaseBound` (requires `building`, `live` and `active`) and `staged()` (requires `building` and `live`) all fail closed. The build then removes its own image through the verified path, and `fail()` on the cancelled row is a no-op. No server is staged for the cancelled forge.
- **Crash in progress.** No build is running. An unrecorded image from the crash is handled by the orphan pass, and a leftover container by the next recover sweep, as before.
- **Optional hardening (Info, may follow):** pass the named forge id to `requeueStale` and filter on it. It is redundant with the unique index, but it would make the scope explicit.
