# Gate 1: R7 PLUGIN-FORGE

## Verdict

**CONDITIONAL_APPROVE.** The shape is sound:
- no bot gets Docker;
- the builder never starts a container and takes the base by id;
- there are two human steps after the work, and only `/mcp approve` activates (`McpRepo.activate` is the only writer of `status = 'active'`);
- the server is write class only, with a DB CHECK.

Nothing needs a redesign. PF-C1 to PF-C14 are contract changes. sa folds them into the spec before BE1 starts, and BE1 or BE2 implements them. PF-C15 to PF-C23 are checked at Gate 2.

Question 2 of the brief, "can the admin read the source?": yes. R5 `ReleaseService.postCopy` posts the pinned zip in #setting above the card, and the card lists each shipped file with its sha256. PF-C14 makes sure a card never exists without that copy.

Scope: the spec, plus code at `e19ff48`: `releases/{service,targets}.ts`, `mcp/{admin,sandbox,host,tool,quarantine,snapshot}.ts`, `db/repos/mcp.ts`, `db/migrations/045-047`, `workspaces/{zip,files,runner}.ts`, `grow/tool-ideas.ts`, `governance/projects.ts`, `admin/keys.ts`, `discord/commands/types.ts`, `devjob/paths.ts`. No scanner was run. There are no runtime dependencies to scan (devDependencies are never shipped). The new base image (`docker/forge/base.Dockerfile`) is scanned at Gate 2 (PF-C23).

## Conditions

### Before BE1 (spec amendment; BE1/BE2 implement)

- **PF-C1 Zip bounded by bytes before any inflate** (§5.4 Z, global rule 13).
  - Read the EOCD and the central directory first. Refuse more than 200 entries, any declared uncompressed size over 512 KiB, or a declared total over 4 MiB, all before the first `inflateRawSync`.
  - The inflate output length must equal the declared size.
  - These must all be 0: external attributes, internal attributes, disk fields and the EOCD comment. There are no bytes between entries or after the EOCD. Offsets are ascending and do not overlap.
  - Exact duplicate names are refused (not only case-folded ones).
  - Tests: 201 entries; 200 × 512 KiB + 1; an entry whose real inflate exceeds its declared size; a duplicate name; trailing bytes.
- **PF-C2 The builder re-proves the bytes** (§3.5, hash chain).
  - Before staging: `sha256(plugin_builds.zip) = plugin_builds.sha256 = releases.sha256` (JOIN), and `validatePlugin(zip).manifestSha256 = plugin_builds.manifest_sha256 = releases.plugin_manifest_sha256`.
  - After the stage dir is written, re-read each file through a no-follow open. Compare its sha256 and size with its manifest entry; matching count and bytes is not enough.
  - Any mismatch → `zip_invalid`.
- **PF-C3 Stage dir hygiene** (global rules 20, 23).
  - Create `tmpdir()/assistant-forge` with mode 0700, then lstat it. It must be a real directory with uid = euid and `mode & 077 = 0`, else `stage_dir`.
  - Files: `O_CREAT|O_EXCL|O_NOFOLLOW`, then an explicit `fchmod 0644`. Dirs: 0755.
  - The boot clean-up (§3.6, "remove `tmpdir()/assistant-forge/*`") becomes this: delete only lstat'ed direct children of the verified parent whose names match `^b-[A-Za-z0-9]{6}$`. No glob, and no symlink is followed.
- **PF-C4 Verify by exact config diff, not a subset** (§3.5 step 7, global rule 6).
  - The base check also requires `Config.Labels` null or {}, `OnBuild` empty and `Healthcheck` null.
  - Then compare the new image's `Config` with the base's `Config` key by key. Only these may differ:
    - User, WorkingDir, Entrypoint and Cmd, each with the exact values;
    - Env, which must be the base Env plus exactly `NODE_ENV=production`;
    - Labels, which must be exactly the three forge labels;
    - a named ignore list (for example Hostname and Image) that the BE3 probe proves `commit` writes.
  - Any other difference is `verify_failed`, for example Healthcheck, Shell, StopSignal, ExposedPorts, Volumes or OnBuild.
- **PF-C5 No orphan images.**
  - Right after `commit` passes its regex, a single-statement UPDATE records `plugin_builds.image_id` (status still `building`).
  - Every exit other than `staged` removes that image (`image rm`, no `-f`, verified) and sets `image_removed_at`. If the removal fails, the `stuck` latch is set.
  - Boot recovery removes the image of a `building` row before it requeues or fails the row.
  - GC also lists `label=assistant.forge=1` images with `--no-trunc`. It removes one only when its `assistant.forge.build` label names a build whose `image_id` is NULL or different, AND rule (c) holds. This covers a commit that timed out on the client but finished in the daemon.
- **PF-C6 Exact container names.** `docker ps --filter name=forge-b` matches any name that *contains* the text. The boot sweep removes only names matching `^forge-b[0-9]{1,12}-[0-9a-f]{8}$` in full. Test: containers named `myforge-bar` and `xforge-b1-deadbeef` survive.
- **PF-C7 Tainted runs cannot request a plugin.**
  - `install_plugin` is refused with a new code `plugin_tainted` when `run.tainted || task.tainted`. It goes after step 8b and before any export.
  - Reason: inside an approved forge project, autopilot runs the software head's web reads without a card. A tainted turn can then write workspace files that an untainted run later releases as a permanent tool (global rule 9).
  - The `install_plugin` card always carries the R5 line "Whether earlier runs that wrote these files read outside content is not tracked."
- **PF-C8 The F8 slug rule re-checked under the McpRepo lock.**
  - In `McpRepo.stage` with `source='release'`, inside the advisory-lock transaction, the stage is refused (`E_EXISTS` → `stage_exists`) unless one of these holds:
    - no row has the slug; or
    - the row is `disabled` or `quarantined`, AND `source='release'`, AND its release's `forge_id` equals this release's `forge_id`.
  - A release stage never overwrites an admin row. Today's ON CONFLICT replaces any disabled or quarantined row, and the request-time check is days older than the stage.
- **PF-C9 A wider `stageRelease` cross-check** (§5.2 `McpRepo.stage`, §6 f).
  - Today the SELECT checks the release status, target, `decided_by` and slug. It must also require:
    - `b.forge_id = r.forge_id`;
    - `b.plugin_slug = r.plugin_slug = $slug`;
    - `b.sha256 = r.sha256`;
    - `b.image_id = $image` (PF-C5);
    - `plugin_forges.status = 'live'`, and its project `active`;
    - the granted departments equal `plugin_forges.dept_id`.
  - Without this, a build already `building` when its project is cancelled still stages a server.
  - The `StageReleaseFn` input type has no command, env, timeout, daily or class field. `stageRelease` hard-codes `[]`, `{}`, 60000, 100 and `write`. A type test proves it.
- **PF-C10 E_CLASS cannot be laundered** (§3.0 F3).
  - A re-add resets `source` to `'admin'` (§5.2), so the `mcp_servers_release_write` CHECK stops binding.
  - `/mcp add` therefore refuses class `read` when ANY of these is true:
    - the image's `Config.Labels` has a key starting with `assistant.forge`;
    - the image id is in `plugin_builds.image_id`;
    - the existing row for the slug has `source='release'`.
  - Labels are read with the forbidden-key guard. An inspect or parse error refuses.
  - The label check can only fail safe: a spoofed label blocks read class, and stripping the label changes the image id, which needs host Docker access.
- **PF-C11 Re-approve after a certain revert.**
  - §3.4 step 1 keeps the inert build row (`ON CONFLICT DO NOTHING`) together with the first admin's `decided_by`.
  - If a second admin then approves, the `r.decided_by = $2` cross-check fails, and the build ends as `stage_state`.
  - The fix: when the conflict row is `queued` with an equal sha256 and manifest, update its `decided_by`. Otherwise refuse.
  - Test: approve → a certain post refusal → another admin approves → the build stages.
- **PF-C12 Reconcile attribution** (§3.2 step 10).
  - The forge becomes `installed`, and the idea is closed, only when every one of these holds:
    - the row is `forge.server_id`;
    - its status is `active` and its source is `release`;
    - its `release_id` belongs to this forge;
    - its `image_id` equals that build's image.
  - An admin re-add of the slug puts the forge back to `live`, as in the disabled case.
  - The idea close is a compare-and-set on `status='open'`.
- **PF-C13 Model-unreachable switches and holders.**
  - `ADMIN_FORBIDDEN_CMD_KEYS` (`discord/commands/types.ts`) becomes `['releases','mcp','forge']`.
  - `forge.enabled` is in HANDLER_KEYS, with a `keys.forge.test.ts` shaped like `admin/keys.mcp.test.ts`. No AdminOp kind touches the forge.
  - Wiring test: only the ReleaseService `TargetDeps` holds the `ForgeEnqueue` closure.
  - NON_SELF_MODIFIABLE also adds `discord/commands/types.ts`, `admin/keys.ts` and `governance/projects.ts` (where the idea link and the taint check live). Neither the forbidden-key list nor the HANDLER_KEYS list is protected today.
- **PF-C14 Never a card without the source.** For `install_plugin`, when `postCopy` returns false, no card is posted. The row stays pending without a card, as on R5's existing path, and the head is told. A Bot Admin can therefore never approve a build blind.

### Checked at Gate 2

- **PF-C15 BE3 layer probe** (residual 7).
  - `docker save` the built `hello` image. The new layer must hold only `srv/plugin/**` entries, regular files and directories only (`/srv/plugin` included).
  - Every entry: uid and gid 0, modes 0644 or 0755, no setuid, setgid or sticky bit, no `.wh.` whiteout, link, symlink or device.
  - Record what `commit --change` writes, and that `cp` into a never-started container works.
- **PF-C16 Argv golden** (FG-AC04).
  - Exact arrays. `cp` has no `-a`, `--archive`, `-L` or `--follow-link`.
  - The `--change` strings carry only a positive integer build id and 64-hex sha256 values.
  - No `run`, `start`, `exec`, `build`, `pull`, `push`, `tag`, `prune`, `system` or `rmi -f`.
- **PF-C17 Switches and halt.**
  - An in-flight build polls `forge.enabled` as well as the halt flag between steps.
  - A halt-requeue does not use up an attempt, or the README says it does.
  - A read error means off at every site: request, decide, tick and notes.
  - The README states the chain: `autopilot.enabled` (projects), `ws.enabled`, `release.enabled`, `forge.enabled`, `mcp.enabled` (calls).
- **PF-C18 Prompt notes.**
  - Idea problem and example sit inside fixed delimiters, and the delimiter characters are stripped from the content.
  - A tainted idea or one closed by a compare-and-set never appears.
  - Notes reach only their own actor. Idea text is never logged or audited.
- **PF-C19 Boundaries.**
  - Run the raw-text scanner with absolute paths, `file:`, dynamic import, `createRequire` and symlinks.
  - `stageRelease` is reachable only through `forgeStageDeps`.
  - `stageRelease` with seccomp false spawns nothing, because it goes through `McpAdmin.probe`.
  - `db/repos/forge.ts` is imported only by `forge/` and `app.ts`.
- **PF-C20 Migration 048** (FG-AC01): up, down, up with rows present. The 048 down also expires open tool approvals for the release-sourced servers it deletes, or documents that their tasks are left waiting. `dept_incidents_kind_check` is confirmed with `\d`.
- **PF-C21 S9 incidents** (§5.11). Only the closed code list. The dept comes from `releases.dept_id`. No free-text column. An unknown code is dropped. The facts are code-built and untainted.
- **PF-C22 Hash-chain test.** The image label `assistant.forge.sha256`, the build sha256, the release sha256 and the card sha256 are all equal. `mcp_servers.image_id = plugin_builds.image_id`. `/mcp show` displays `forge:release-<id>`. The 047 pin covers the image id.

- **PF-C23 Base image and its pin** (brief item 1, global rule 21).
  - Scan: a binary-aware scan (trivy or grype, with a positive control) of the image that `docker/forge/build.sh` produces. Any unpatched HIGH or CRITICAL is a REJECT. npm, npx, corepack and yarn are absent from the final image.
  - Pin control: only the owner's `build.sh` writes `docker/forge/images.json`. `docker/forge/` is NON_SELF_MODIFIABLE, and no bot has repo write. The app reads the id once at boot and checks it against `IMAGE_ID`. A changed file takes effect only after a restart, and the §3.6 base check runs again then.

## Notes on the checked items

- **Runtime (item 5).** The R6 sandbox still holds: no network, read-only, uid 65534, `cap-drop ALL`, a fresh container for every call, no persistence, the snapshot hash checked on every call, write-class cards, and output marked untrusted.
  - "Bots wrote it" changes one assumption: the tool descriptions are now written by the party that will benefit from steering the model. The description screen and the MC-C7 view stay as they are.
  - Every call is a human card, and the result taints the run (residual 3).
- **Squatting (items 4 and F7).** Any head can file ideas. `forge_cap` 3 and proposal expiry after 7 days (`ProjectService` expiry sweep) bound how long an idea can hold a slot. A bot-chosen slug can impersonate a well-known name; the admin sees it at install. Low.
- **DoS (item 6).** 3 builds a day, 1 at a time, 8 kept images of at most 8 MiB each, a 4 MiB staging dir and 180 s per build. These are acceptable.

## Residual risks (plain words)

1. The app can still reach Docker. A Docker or kernel flaw could let a plugin escape when it runs.
2. Files written by earlier tainted runs in the same workspace are not tracked. PF-C7 only stops the requesting run.
3. A bot writes the tool descriptions and results that other bots read. They are screened and marked, but they can still nudge a bot.
4. A plugin can answer wrongly for some inputs without changing its tool list.
5. Approving means trusting the admin's reading of the source copy. Long source can hide harm.
6. Every call is a card, so admins may tire and click through.
7. Anyone with DB write access can edit forge, release and server rows. The 047 pin is a tripwire, not a signature.
8. A flaw in the base Node image is in every plugin until the owner rebuilds it.
