# Security Gate 1: HEAL-1

Verdict: **APPROVED WITH CONDITIONS**. The conditions are HL-C1 to HL-C20. They bind the build, the tester (HEAL-T1/T2) and Gate 2 (HEAL-S2).

The design keeps the main guarantees:
- Code derives every trigger, decider and flag.
- Untrusted title and note text reach a run only inside the untrusted wrapper.
- Taint is copied forward.
- The footer is built after the model has finished.

Three gaps need fixing before build:
- **F-1.** A block, roll-up, retry loop has no bound.
- **F-2.** The quiet lift applies to every guard key, and nothing caps it on the local provider.
- **F-3.** `resolve_blocked` can unblock tasks blocked for budget or approval reasons.

Anchors are function names plus quoted fragments. Line numbers are hints only.

## Cited facts checked (corrections to the brief)

- **WS1 lifts more than the hourly rates.** The schema comment under `limits.localUnlimited` and `localRefusal` show that a local call also skips `warroom.localCallsPerDay` and `limits.turnsPerTask`. On the local provider, only the stall count bounds bot talk. The brief's S2 understates this.
- **The guard covers every bot-talk key.** That means #ai-warroom, department rooms, forum posts and task threads (warroom.ts header). A `liftIfQuiet` placed in the generic `isStalled` and `start()` (C6) therefore lifts stalls everywhere, not only in the warroom that H3 names.
- **Every new stall grants one more CEO stall turn** (`start()`: "t.stalled = { ceoTurn: true }"). One window is therefore stallTurns + 1 runs.
- **C8's premise is wrong.** `prune()` runs only when "this.states.size >= MAX_KEYS" (500), so an idle key does not lift after 6 h by itself. The 15-360 range is harmless (it only limits how long the owner can make the quiet period), so it can stay. The reasoning in C8 should be corrected (BOOK).
- **Praw can lift the warroom (H3a).** Praw has `tools: ["*"]`, and any guild member can reach it with `/ask` (origin `slash`). So H3a lets any guild member lift the #ai-warroom stall through Praw or a head, without warroom access. Today TW3 needs a person who writes in the private room.
- **`ask_requester` does not reach a person on the CEO path.** On a decide task its target is HQ itself, because the requester of a decide task is HQ. So on the CEO path, "ask the person" does not reach a person.
- **A cancelled task cannot be brought back.** `/task retry` and `retryBlocked` act on `blocked` only. A cancel is therefore irreversible.
- **The audit field is long enough.** `cap()` keeps 200 characters, so `ok #n <runTaskId>` (about 42 characters) is never truncated.

## Rulings

**G1-a: should `cancel` be refused from a tainted run? Yes, but only for tasks a person asked for.**

Why:
- A cancel cannot be undone.
- The blocked note is written by the member's own run, which is the injection channel the decider reads.
- A tainted owner can already end its own task with `update_task done`. So cancelling a *delegated* (bot-made) subtask adds little power, and the head can delegate again.
- Losing work a person asked for is the harm worth refusing.

The rule is HL-C6. A refused task stays blocked and is listed for the owner. Retry from a tainted run stays allowed, because the taint is copied to the child.

**G1-b: is the quiet-lift worst case acceptable? Not as written. With bounds, yes.**

The bounds:
- H3b is limited to the #ai-warroom channel key (HL-C1).
- Two separate daily caps, neither of them on the WS1 lift list (HL-C2):
  - `warroom.quietLiftsPerDay` (default 3) for H3b;
  - `warroom.personLiftsPerDay` (default 4) for H3a runs whose person is not a Bot Admin.
- An H3a run by a Bot Admin (`msg.isAdmin`) is not capped. That matches writing in the room, and it means nobody else can use up the owner's lift (global rule 10).

Worst case in #ai-warroom with no Bot Admin involved, at the defaults:
- The first window is up to 2 x 20 + 1 = 41 runs, because of the one taskWrite reset (WS3).
- Each later window is 21 runs, because `lift()` sets `resetUsed=true`.
- Quiet lifts alone: 41 + 3 x 21 = **104 runs a day**.
- Adding the non-admin person lifts: 104 + 4 x 21 = **188 runs a day**.

Today it is 41. Other keys are unchanged.

### resolve_blocked

- **HL-C6 (G1-a).** `cancel` is refused with `R_TAINTED` when both of these hold:
  - `ctx.tainted() || ctx.task.tainted`;
  - `isHumanOrigin(blocked.origin)`.

  The refusal text is "a person asked for that task; it cannot be cancelled from a run that read outside text. Retry it or leave it for the owner". The audit row is `refused:R_TAINTED`. The task is listed in the summary as "needs owner".

  Test matrix: {tainted, clean} x {`chat`/`slash` origin, `delegated`}. Only tainted + human origin is refused.
- **HL-C7 (F-3).** Refuse unless `blocked_reason` ∈ {`owner`, NULL, `error`, `turns`}, with `R_NOT_HEALABLE` "that block needs the owner". The check sits after `R_NOT_BLOCKED`.
  - Tests: `budget`, `approval` and `halt` are refused for both actions.
- **HL-C8 (F-1).** `retry` is refused with `R_RETRY_CAP` once the task has `heal.maxWakesPerTask` `task.heal.resolve` rows with outcome `retry` over its lifetime.
  - Test: a child that re-blocks after each parent retry gets at most 2 retries at the defaults, and the third gives `R_RETRY_CAP`.
- **HL-C9 (brief C1, 3.4).** Authorisation for `resolve_blocked`:
  - The tool declares no `kind` and has `requiresApproval: () => false`.
  - When `deciderOf` returns `none`, every caller is refused.
  - Rule 7 parses the run-task id from `ok #n <id>`.
  - Tests:
    - a snapshot asserts `kind` is undefined;
    - calls from a tainted, non-direct run create no approval row;
    - refused callers: persona, member, a head that is not the decider, a decider in an unrelated conversation (`R_NOT_HERE`), a sibling tree, a `none` task;
    - a pending approval gives `R_PENDING`;
    - open children on cancel give `R_OPEN_CHILDREN`.
- **HL-C10 (F-4, brief C12).** The rows that carry a cap (`task.autoretry`, `task.heal.wake`, `task.heal.resolve` retry) are written claim-first:
  - They use an awaited insert that throws on error, not the swallowing `audit()` helper.
  - If the insert fails, the action is skipped for that tick.
  - A claim counts toward its cap even when the action is then refused.
  - The summary's "unblocked" count comes from task state, not from rows.
  - Test: a failing insert means no retry and no wake.

### Footer (H4)

- **HL-C15 (brief 3.6, F-7).** How the footer is built:
  - Reasons come only from registry results of known tools (`registry.has`).
  - An untrusted tool gives the fixed text "the call failed".
  - The text goes through `escapeCardText(fold(reason),160,deps.secrets)`, then `https?://` is defanged to `hxxp(s)://`.
  - The footer is built in `finish` after the last provider call, so the model never sees it.
  - With streaming, the final edited message ends with the footer.
  - The footer is added to every payload type `respond` can return that has a body.
  - If the builder throws, the answer is posted without the footer and the log has `errName` only.
  - Tests:

## Who can trigger what (global rule 10)

- **Retries and wakes:** code only (`system:healer`).
- **`resolve_blocked`:** only the code-derived decider head, from the parent task or its decide task.
- **Lifting the warroom stall:**
  - any guild member who writes in the room (as today);
  - a Bot Admin through an untainted Praw or head run, with no cap;
  - any other guild member the same way, sharing 4 lifts a day;
  - the quiet timer, at most 3 lifts a day.

  No one but a Bot Admin can use up a Bot Admin's lift.

## Residual risks the owner signs (plain words)

- **RR-1.** The warroom bot chat can restart without you:
  - 3 times a day on the quiet timer;
  - 4 more times a day when any server member asks Praw or a head to post there.

  That is about 188 bot turns a day at most, against 41 today. Bot Admins can always lift it.
- **RR-2.** Retries and wakes spend money and local compute without anyone asking. The limits per task:
  - 1 run + 2 automatic retries + 2 head retries;
  - 2 decider wakes;
  - 10 wakes per head per day.

  Normal budgets still apply.
- **RR-3.** A head that has not read outside text can cancel a blocked task on its own judgement. That includes a task a person asked for, even a top-level one. A cancel cannot be undone. Each cancel is listed in the daily summary.
- **RR-4.** A deciding head reads the blocked member's note and title, which may contain text planted from a web page. It is wrapped, and the run is tainted, but a tricked head can still retry with a bad instruction (twice at most).
- **RR-5.** The "Not done" line can show an error text that a plugin copied from outside, masked and escaped. It can also miss a failure when a later call of the same tool succeeds for a different target.
- **RR-6.** Department-room and task-thread stalls still need a person. Tasks a person asked for that a tainted run cannot cancel wait for you in the summary.
