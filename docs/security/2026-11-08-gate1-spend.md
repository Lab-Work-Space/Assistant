### Deadlock analysis (lock order)

All row locks on budget_days are taken in `lockRows()`: inserts in key order, then `FOR UPDATE` in key order. Each transaction holds at most one row per scope. The new layouts are ordered subsequences of the new global order:

- normal `[company, dept, bot, task?]`
- warroom `[company, dept, task?, warroom, warroom_bot]`
- local `[task?, local, warroom?]`
- the `close()` and `onLocalAttempt()` paths reuse the stored `res.keys`, so they follow the same order

Mixed key days are harmless: the company row uses the UTC day and the dept row uses the local month, and ordering is by scope. The insert phase also follows the global order, so a wait on an uncommitted insert cannot form a cycle; this is the same argument as today.

Other lockers checked:

- `approvals.ts` cap-hit and `decide()`, and OT-1 approve: these lock `tasks` root FOR UPDATE, then only SELECT budget_days, so they take no budget_days lock.
- `close()`: locks budget_days rows, then the `tasks` row (`cost_usd`). It never waits for budget_days while holding `tasks`, so there is no cycle.
- `spend_overrides`: the approval UPDATE and the onStop INSERT run in their own transactions with no budget_days lock. `deptCap` only reads it (MVCC, so it never waits).
- `spend_days`: the upsert is one row, last in `close()`. Prune deletes only days older than `retentionDays` (≥ 90), and reserve-time days are at most one day old, so the two never touch the same row.

Remaining risk: pool starvation if `deptCap` or the persona dept lookup used `pool.query` instead of the transaction's `client` while row locks are held (30 parallel reserves × 2 connections). S9 binds this.

## Binding conditions for Gate 2

S1. **No model path.** Every spend.* key is in `HANDLER_KEYS`. For each spend.* key, `isAdminConfigKey(k) === false` and console `config_propose` refuses it. `AdminOp.safeParse` fails for `{op:'budget_set',scope:'dept',...}` and for any op name containing `spend`. `PANEL_LIVE_KEYS` contains no spend.* key. `BUDGET_SCOPES` does not gain `dept`: `/budget dept` is its own `COMMAND_TABLE['budget:dept']` handler. Dashboard `/propose` refuses spend.*. Tests: `discord/commands/settings.test.ts` (pattern of the existing isAdminConfigKey test), `admin/console.int.test.ts`, `admin/settings.test.ts`, `admin/panel.test.ts`.

S2. **Override decision path.** `spendovr:` is routed only by `route()`, which runs after the CONFIG_CHANNEL_ID and live admin-role checks in `decide()`. It is never added to the early `admincfg:` or category-room `approval:` branches, and it is listed in `deferEphemeral`. The handler parses `^spendovr:([0-9a-f]{32}):(approve|reject)$` exactly. It requires `i.messageId === row.message_id` and `row.channel_id === CONFIG_CHANNEL_ID`. It uses the conditional UPDATE from spec D.5. The card is posted by the hq bot. Tests: `discord/commands/commands.test.ts` covers an off-channel click, a non-admin click, a malformed id, a message id mismatch, a double click (one winner), and an expired card.

S3. **SP-01 maximum.** A single `SPEND_MAX_USD = 999999.99`, or `numeric(14,6)` columns. When old cap ≥ max or new ≤ old, there is no card and the alert says so. Tests: `governance/spend.int.test.ts` (cap at max, 1e6 rejected by the schema), `db/migrate.int.test.ts`.

S4. **SP-02 re-arm.** After an approved raise is used up, the next dept refusal in the same month and process produces a new card. Test: `governance/spend.int.test.ts`.

S5. **SP-03 stale pending.** Expire stale pending rows in the onStop transaction. A failed card post leaves no blocking pending row. Tests: `governance/spend.int.test.ts` (a pending row past expiry is not yet pruned and a new stop still creates a card; a post failure followed by a new stop creates a card).

S6. **Override bounds.**
- `new_cap = ceil_cent(max(used+est, max(cap,1)×(1+step/100)))`, clamped to the maximum.
- Rejection: after a rejection, no new card that month (alert only).
- Concurrency: 10 concurrent stops produce exactly one pending row and one card.
- Effective cap = max(config, approved overrides), read through the transaction `client`.
- Month binding: an approval for month M has no effect on month M+1.

Tests: `governance/spend.int.test.ts`.

S7. **Expiry.** `expires_at = least(now()+expiryHours, start of next local month)`. The month start is computed from `schedule.timezone` passed in explicitly, never from the PG session timezone. Test: in Asia/Bangkok, a card created on 2026-11-30 at 16:00Z expires at 2026-11-30 17:00Z, and an approve click at 17:00:01Z is refused. File: `governance/spend.int.test.ts`.

S8. **SP-05 supersede.** A human `/budget dept` or `/settings set spend.deptMonthlyUsd` change expires approved and pending overrides for (dept, current month), audited. The reply shows the effective cap. Tests: `governance/spend.int.test.ts`, `discord/commands/commands.test.ts`.

S9. **Lock order and connections.**
- The `KeyScope` type and the lock-order comment in `budget.ts` are updated.
- Key layouts are exactly as in spec A.3; local layouts never include dept.
- `deptCap` and the persona dept lookup use the transaction `client`.
- The spend_days upsert is the last statement in `close()`.
- No code path locks spend_days or spend_overrides and then budget_days.

Tests: `governance/budget.int.test.ts` (30 parallel reserves on one dept, pool size ≤ 10, no overshoot and no timeout; exactly at cap is allowed), `governance/budget.warroom.int.test.ts` (warroom layout locks the dept row), and a mixed concurrent test (metered + local + warroom + settle on the same root) that finishes without deadlock.

S10. **Rollup sanitisation (SP-06).**
- tool `^[a-z0-9_]{1,40}$`, else `other`.
- provider charset per SP-06, else `unknown`.
- model charset per SP-06, else `''`.
- dept `^[a-z_]{1,32}$`, else `_unattributed`.
- Attribution never changes a limit decision.
- Media keeps no top-level `provider`/`model` in its reserve call (RF28/RF29) and passes only `attribution`.

Tests: `governance/budget.int.test.ts` (NUL, emoji, 200-char and empty values are booked as fallbacks; settle succeeds; the same request with different attribution gives the same decision), `tools/plugins/media/media.test.ts` (reserve argument shape).

S11. **Fail closed.** A forced rollup failure (for example a CHECK violation, simulated with a trigger in the test) makes settle throw. budget_days and `tasks.cost_usd` stay unchanged. The reservation stays held. `callProvider` returns `meter/settle`. Tests: `governance/budget.int.test.ts`, `agents/loop.int.test.ts`.

S12. **Clocks.**
- `localDay` uses `Intl.DateTimeFormat(...).formatToParts` with `schedule.timezone`.
- The month and rollup day are captured on the Reservation.
- A settle after local midnight or month end books to the reserve-time keys.
- Company, bot and task days stay UTC.

Tests: `governance/budget.int.test.ts` (Asia/Bangkok, reserve at 2026-11-30T16:59:59Z, settle at 17:00:01Z, dept month stays 2026-11-01), `discord/commands/commands.test.ts` (" (UTC)" titles).

S13. **Dept resolution for local calls.** The rollup gets the dept (head or persona lookup) for local calls too, without creating or locking a dept row. A local release with no attempt books calls ≥ 1, as the spec says. This is documented as accepted. Test: `governance/budget.int.test.ts`.

S14. **Alerts (SP-10, SP-11).**
- Claims: INSERT ON CONFLICT DO NOTHING; claims survive a restart.
- Retries: attempts are incremented before the post, with at most 3 attempts, then log and incident.
- Anomaly: the USD floor applies when the median is 0.
- Weekly summary: the ISO week-year is used; a Monday holiday catches up on Tuesday.
- `spend.alertsEnabled=false` stops warn, anomaly and projection but never the stop alert or card.

Tests: `governance/spend.test.ts`, `governance/spend.int.test.ts`.

S15. **One stop alert (SP-04).** Exactly one #🧾-bot-log alert per dept stop claim. `budgetPausedAlert` never produces the bot or UTC fall-through text for dept. Tests: `agents/scheduler.test.ts`, `governance/spend.int.test.ts`.

S16. **Post content.**
- Alerts, the weekly summary and the override card hold only amounts, percentages, dept ids, provider, tool, model, the month or ISO week, and task `#<id8>`.
- They never hold a task title, user text or a person's name.
- They are sent with `allowedMentions: {parse: []}` and ids are code-formatted (SP-13).
- Alerts and the summary go to `BOT_LOG_CHANNEL_ID`; the card goes to `CONFIG_CHANNEL_ID`.
- `/usage trend` stays a Bot-Admin configReply.

Tests: `governance/spend.test.ts` (a task title planted in the DB never appears in the output), `discord/commands/commands.test.ts` (trend ≤ 25 fields, each value ≤ 1024, total ≤ 6000).

S17. **Dashboard.** `GET /spend` is session-gated like `/audit`. The page has no form, script or POST route (POST /spend returns 404). Every string is HTML-escaped. `spend_alerts.detail` is rendered through a field allowlist, never as raw JSON. The page exists only in local mode (127.0.0.1). Tests: `dashboard/server.test.ts` (unauthenticated → login; a `<script>` planted in model/provider renders escaped; POST rejected).

S18. **Migration (SP-07).** The backfill sanitises dept. Up then down then up is clean. Down removes the dept rows. `Budget.usage()` excludes `scope='dept'`. The migration test runs alongside 030 and 031 present. Test: `db/migrate.int.test.ts`.

S19. **Config bounds.** Every spend.* number is finite and rejects NaN, ±Infinity, 1e308 and negatives (the D4 pattern). These count as loosening, so `/settings` posts the risk notice:
- deptMonthlyUsd raised or cleared
- warnPct raised
- anomalyMultiplier raised
- anomalyMinUsd raised
- alertsEnabled or weeklySummary set from true to false
- overrideStepPct raised
- retentionDays lowered

The SP-09 timezone risk flag is also added. Tests: `discord/commands/settings.test.ts`, `admin/settings.test.ts`.

S20. **Refusal text.** `budgetText`, the media refusal and the metered error each have a dept branch. No dept refusal reads "bot". Tests: `agents/loop.test.ts`, `tools/plugins/media/media.test.ts`.

## Residual risks (owner acceptance required)

- R1. Local (claude-code-local) calls are never limited by a dept budget (L8). Moving a dept to the local provider (an admin_op `bot_model` card) takes it out of dept control. The other caps still apply.
- R2. `_unattributed` (deleted persona, unknown actor) has no dept cap. The company, bot and task caps still apply.
- R3. A mid-month timezone change shifts the month bucket by at most about one day, which can mean one extra monthly cap at most (SP-09 flags the card).
- R4. The backfill uses UTC days with unknown provider and tool. In the migration month the enforced MTD starts at the migration time.
- R5. Devjob spend is outside spend_days, trends and dept caps. It keeps its own `devjob.budgetUsd`.
- R6. Media settle above the reservation can overshoot a dept cap by at most one generation (as today for company, bot and task). A media settle failure only logs (the reservation stays held until a restart).
