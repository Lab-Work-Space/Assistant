# Security Gate 1: GROW-1

Verdict: **APPROVED WITH CONDITIONS**. Conditions GW-C1 to GW-C27 bind GW-P1, GW-BE1..BE3, the tester (GW-T1/T2) and Gate 2 (GW-S2). Owner decisions G1-G3 are taken as given. This gate bounds them; it does not reopen them. "Brief" means the SA brief; section numbers are its own.

What the design gets right:
- The judge sees only the stored, re-screened, re-linted proposal, inside nonce wrappers (`wrapUntrusted` in prompts/assemble.ts escapes look-alike tags and does not truncate).
- A skill cannot add a tool: `propose` copies `tools = existing.tools` on an edit and `[]` on a create, and `applyProposal` check (g) closes the proposal stale if `!same(cur.tools, p.payload.tools)`.
- The cap claim and the halt/switch re-check are inside the skill transaction (`SkillRepo.tx`, "pg_advisory_xact_lock($1)", WRITE_LOCK = 7_311_031).
- `tool_request` is never routed to the judge. It uses its own table, token and `toolreq:` prefix, and approve uses `cfg.setIf` (CAS) on the whole `tools.byDept` map.
- New tools sit in `builtinNames`, so neither `tools.byDept` (`plugins()` filter, app.ts) nor a skill (rule G) can grant them.

Gaps that must close before build:
- **F-1.** RETRO_TOOLS is placed on the offered list only. The registry dispatch list could still allow `create_task` (GW-C1).
- **F-2.** The owner's rollback is not durable. A head can re-propose the rolled-back or rejected text and the judge can apply it the next week (GW-C10).
- **F-3.** Boot recovery cancels open retro tasks only where `outcome IS NULL`. A retro task whose `closeRetro` failed is reset to `todo` and runs as a plain owner run (GW-C6).
- **F-4.** Untaint-by-construction is only claimed, never proven through the real thread, history and provenance (GW-C4).
- **F-5.** F2 trusts `tasks.tainted` alone. Outside-origin tasks (`watch`, `import`, `poll`) can carry `tainted=false` when a caller passes it explicitly (GW-C5).

## Rulings

- **R1 (an AI-applied skill steers a team): accepted with GW-C7..C15.**
  - Bounds: code checks before the judge; hash binding; caps and halt/switch claimed in the tx; no tool can be added; rollback is made durable (GW-C10); digest plus applied notice.
- **R2 (cost): accepted.**
  - One claimed run per dept per ISO week, never retried; warroom pool; existing budget caps.
- **R3 (planted text in facts): accepted with GW-C3..C5.**
  - The facts come only from untainted rows, the message is wrapped, and the proposal still meets lint, the code checks and the judge.
- **R4 (risky tool ideas): accepted with GW-C24.**
  - No code reads `tool_ideas` in GROW-1. E must treat ideas as untrusted and pass its own gate.
- **SA (a) RETRO_TOOLS:** approved, with GW-C1. `kb_search` taints the run on unverified documents, so it fails closed.
- **SA (b) async judge, neutral reply:** approved. The reply must not claim success (GW-C13).
- **SA (c) tool_idea from tainted runs:** approved. The taint is stored and shown, and there is no consumer in GROW-1 (GW-C24).
- **SA (d) no re-post of a failed card:** approved. The row expires in 7 days and is listed in `/tool requests`.
- **SA (e) a missed slot is not caught up:** approved (fail-safe).
- **SA (f) applied notice in #setting:** approved. Ids, version and dept only; never skill text.

## Binding conditions

### Retro (GW-BE1)

- **GW-C1 (F-1).** The RETRO_TOOLS intersection is applied inside `allowedFor` in loop.ts, so the offered list and `toolBase.org.toolsFor` are the same list. The `noSay` filter moves into `allowedFor` the same way.
  - Test: a retro run whose model calls `create_task`, `forward_to` and `warroom_say` by name is refused by the registry (`unknown_tool` or not-allowed), and no task is created.
- **GW-C2.** `trigger.retro` is set only in `Scheduler.retroRun`.
  - Test: grep finds exactly one writer, and no path that builds a trigger from a Discord message or an API can set it.
  - The `context.includes('UNVERIFIED: ')` / `roomTainted` taint line stays unchanged. Filtering happens before `assembleContext`, so a filter bug fails closed.
- **GW-C3.** Under `trigger.retro`:
  - deptNotes are filtered to `!tainted`;
  - lessons starting with `UNVERIFIED: ` are dropped;
  - roomEntries are filtered to `!tainted`.
  - Test: one seeded tainted note, one UNVERIFIED lesson and one tainted room entry are absent from the prompt, and the run is untainted.
- **GW-C4 (F-4).** An int test drives the real `Scheduler.retroStart`, with real `ensureThread`, `history`, provenance store and `approved`, and only the model faked. It asserts:
  - `run.tainted()` is false when `skill_propose` executes;
  - the proposal row is created.
- **GW-C5 (F-5).** Rule 9 inventory. The retro reads only the brief's F1-F8 sources and the guard on each:

  | Source | Guard |
  | :--- | :--- |
  | Task titles | `tainted=false` (F2 must also add `origin NOT IN ('watch','import','poll')`); `update_task` cannot write titles |
  | dept_notes | `tainted=false` |
  | Lessons | the UNVERIFIED filter |
  | Room entries | `!tainted` |
  | Skills | written only via proposals that refuse tainted runs, or by admins |
  | Proposals | ids and codes only |
  | audit_log | tool names and codes only, regex-filtered |

  - The facts never read `tool_ideas`, `tool_requests.reason`, `skill_proposals.ai_review` or `payload`. Any new source needs a re-gate.
  - Test: a tainted task title and an outside-origin task title with `tainted=false` are both absent from the facts.
- **GW-C6 (F-3).** `closeOpenRetroTasks` cancels every non-terminal task whose id is in `retro_runs`, whatever the outcome. It runs before the doing→todo reset.
  - Test: a `retro_runs` row with outcome `done` and its task still `doing` is cancelled at boot, and no owner run starts. The boot-order test sits beside heal.int.test.ts.
- **One skill per retro claim.**
  - `claimSkill` is a single conditional UPDATE.
  - The release runs on both a not-ok return and a thrown `createProposal` (try/finally).
  - Test: two `skill_propose` calls in one tool batch give one proposal and one `retro_skill_used`.
  - This sits under GW-C2, because the claim is keyed on the task id. A non-retro run on a retro task stays capped by the same row.

### Skill judge and applyCore (GW-P1, GW-BE2)

- **GW-C7.** `applyCore` AI mode:
  - acts only on status `open`. Any other status (card, rejected, stale, applied, withdrawn) returns `gone` and writes nothing;
  - writes `by` and `reviewed_by` as `system:ai-approver` on every write it makes, including `stale()`, `closeProposal` and `insertAttachment`;
  - runs checks (a)-(g) unchanged.
  - Card mode keeps the `applyProposal` signature, and the existing tests in admin/console.skill.int.test.ts and skills/service*.test.ts pass unchanged.
- **GW-C8 (hash binding).**
  - The judge's user text is built only from `rev.body` (and `renderBlock(rev.current)` for an edit) returned by the same `review()` call, never from `p.payload`.
  - That call's `rev.sha256` is the `expectSha` passed to `applyByAi`.
  - `applyByAi` has exactly one caller, `SkillJudge` (grep test).
  - Test: a payload changed after review closes the proposal `stale`.
- **GW-C9 (no tool by construction).** In AI mode:
  - a create with `payload.tools.length > 0` escalates `apply:tools`;
  - an edit must pass check (g).
  - Test: a seeded create row with tools is never applied.
- **GW-C10 (F-2, durable rollback).** Before the judge is called, code escalates on any of these:
  - `human_version`: the current active version's `source` is `admin`, `rollback` or `seed`;
  - `not_active`: the skill status is not `active` (disabled);
  - `rejected_before`: a proposal for the same `skill_id` was `rejected` in the last 30 days.
  - Tests: one per code.
- **GW-C11.** The pre-judge code checks run in the brief's order: halt, `review()`, target, URL, mask, cap peek, size ≤ 16000. Then the throwing start row is written, then the judge runs. Every check, error, timeout, bad output or exception in `offer()` escalates. Nothing applies on error.
  - Test: one per escalate code, and an exception thrown inside `offer` still posts the human notice.
- **GW-C12 (tx re-check).** `beforeCommit` runs only on the success path, after every write and before COMMIT. It:
  - reads the switch and halt from memory only;
  - counts caps and inserts the claim on `t.c` only, never on the pool (the AI-APPROVE G2-01 deadlock lesson);
  - throws `SkillRefused` on any refusal, so the whole tx rolls back and the proposal stays `open`.
  - The cap peek and the claim share one week-start SQL. A max of 0 always escalates.
  - Tests: no claim row on stale, refused or rolled-back paths; two concurrent applies with `maxPerDeptWeek` 1 give one apply.
- **GW-C13 (judge isolation).**
  - The judge call has `tools: []`, `maxTokens: 200` and a system text of only `AI_SKILL_JUDGE_SYSTEM` (snapshot test). It gets no persona, skills, notes or lessons.
  - Logs carry `errName` only.
  - `ai_review` comes from `sanitizeReason` (≤200) and is shown only on the #setting notice and `/skill review`. It never enters any prompt.
  - The head's reply text says NOTHING has changed.
- **GW-C14 (F-6).** `recover()` also escalates `interrupted` any proposal with `status='open'`, `ai_review IS NULL`, `created_at > now()-24h`, no start row, created while `skills.ai.enabled` was true.
  - A simpler alternative: any such proposal without a `skill.review` card audit row.
  - In both cases the human notice gets posted. Never judged again.
- **GW-C15.** The JudgeCaller refactor leaves governance/ai-approver.test.ts passing unchanged. The skill judge's concurrency is 1. `skills.ai.enabled` defaults to false, and deploy confirms false.

### tool_request (GW-BE3)

- **GW-C16.** `tool_request` never writes `approvals`, never emits `approval.requested` and has no `kind`.
  - Test with `approval.ai.enabled=true`: no approval row and no judge call.
- **GW-C17.** `toolreq:` is routed only in `route()`. It is never added to the pre-check branches of `decide()` (the `admincfg:` and `approval:` branches).
  - Tests: a click from another channel and a click from a non-admin are both refused before the handler.
  - `TOOL_REQUEST_ID` is anchored. A model payload cannot set `toolRequestId` (toPayload test).
- **GW-C18.** The request-time refusals run in the brief's order. `not_head` covers praw and personas, `halted` is checked by the tool itself, and `tainted` reads `ctx.tainted() || task.tainted`.
  - Rule G (`skillToolAllowed`) runs at request time and again at decide.
  - Decide re-checks halt, `tools.names()` and `planBotTools` fresh.
  - `setIf` expects the plan's `before` map. Test: only `tools.byDept[dept]` differs before and after.
- **GW-C19.** Decide refuses unless the row found by token has stored `channel_id` and `message_id` equal to the click's, is `pending` and is unexpired. One conditional UPDATE wins.
  - Tests: a double click gives one write; a CAS loss reverts to `pending`.
- **GW-C20 (F-7).** The claim UPDATE sets `outcome='applying'`, and the success path sets `outcome='ok'`.
  - At boot, rows that are `approved` with outcome `applying` are reconciled: `ok` if the tool is in `tools.byDept[dept]`, else back to `pending` if unexpired, else `void`.
  - Audit `bot.tools.add` is written only after `setIf` succeeds.
- **GW-C21.** A request for a (dept, tool) pair rejected in the last 7 days refuses with code `recently_rejected` and a fixed text. This stops card spam and social engineering by repetition.
- **GW-C22.** The head notices go through `Scheduler.post` with provenance `{tainted:false,userId:null}`, are code text only, and carry a tool name that matches `SAFE_TOOL_NAME`.
  - Test: the provenance row exists, and the next run in that room starts untainted.

- **GW-C23.** The pending cap (3) and the duplicate check sit in one tx with `pg_advisory_xact_lock(7311040)`.
  - Test: 4 concurrent requests give 3 rows. The sweep expires rows, closes the cards and notifies the head. It also runs at boot.

## Who can trigger what (global rule 10)

- **Skill judge:** with `skills.ai.enabled`, any untainted head run reaches it, not only the retro. That includes a guild member chatting with a head in its room. Bounds: 1 apply per dept per week, 5 per week, GW-C10, digest, rollback.
- **Tool requests:** any untainted head run can file one. Effects: at most 3 pending cards per dept, and GW-C21. Only a live Bot Admin in #setting can approve.
- **Tool ideas:** any head run, tainted ones included, can file one; at most 5 open per dept.

## Residual risks the owner signs (plain words)

- **RR-1.** With the AI switch on, a team skill can go live without any person reading it first. Anyone who can chat with a department head can try to get one written. At most 1 per team and 5 a week. You see each one in the daily digest and can undo it.
- **RR-2.** An approved skill shows up in the next retro's prompt, so the AI builds on what the AI approved. Undo is durable: a rolled-back, disabled or rejected skill goes to a person next time.
- **RR-3.** Task titles and notes written by the bots can still nudge a retro proposal. The judge and the caps are the bound.
- **RR-4.** A Bot Admin can be talked into approving a tool request by its reason text. The card says the text was written by the bot.
- **RR-5.** Each retro costs one head run per team per week.
- **RR-6.** Tool ideas may come from runs that read outside content. They are marked, and nothing is built from them in GROW-1.
