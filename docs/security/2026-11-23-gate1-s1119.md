## Findings

**S1119-01 — Medium — §11.19.9 vs `core/db/backup.py:107` (`restore_knowledge`): the old knowledge dir is kept forever.**
- **Evidence:** `os.rename(dest, f"{dest}.old-<ts>")` leaves `/var/lib/employee/knowledge.old-<ts>`, and nothing ever deletes it.
  - `_prune_old` (L46) matches only `daily|pre-migrate|knowledge-*.{db,tar.gz}` inside `backups/`.
  - `KnowledgeStore.erase_user`/`purge_older_than` act only on the live dir.
- **Impact:** after any restore, a full copy of the transcripts escapes both the 14-day erasure bound (S11-03) and the knowledge retention purge, with no time limit.
- **Change (database, test-first):** after a successful `os.rename(tmp, dest)`, call `shutil.rmtree(old)`, as the spec block does (spec L306–L307). Then change `test_knowledge_restore_swaps_and_keeps_old` (tests/test_db.py:359) to assert that no `knowledge.old-*` entry remains.

**S1119-02 — Low — `core/db/backup.py:106-111`: no rollback when the second rename fails.**
- **Evidence:** if `rename(dest, old)` succeeds and `rename(tmp, dest)` then fails, the `except` branch only removes `tmp`, so `dest` is missing.
- **Change:** in the `except` branch, add `if not os.path.lexists(dest) and os.path.lexists(old): os.rename(old, dest)`, keeping `old` in a variable (spec L301–L303). Add the T-DB-13 test with `os.rename` patched to fail on its second call.

**S1119-03 — Medium — §11.19.9 restore runbook (L338), §11.19.10 Hostinger restore rule (L366), OQ-13: restores bring back erased transcript content.**
- **Evidence:** `erase_user` and `delete_entry` (store.py:249, :275) leave no record of themselves.
  - The knowledge restore relies on the owner remembering which erasures to re-apply.
  - The Hostinger whole-disk restore rule re-applies only `voice_optouts`.
- **Impact:** a data subject's erasure request is silently undone by a restore.
- **Change (sa + backend, before release):** add an erasure ledger.
  - **Table:** `knowledge_erasures(area, file, user_id_hash, kind, at)`, with no content and the hash keyed by a fixed salt.
  - **Writes:** every `erase_user`/`delete_entry` appends a row.
  - **Knowledge restore:** re-applies the ledger rows newer than the archive timestamp.
  - **Hostinger restore rule:** extend it to "export `voice_optouts` **and** `knowledge_erasures` from the pre-restore host and re-apply both". When the pre-restore host is unreadable, the consent-gap marker also blocks serving knowledge entries, until the owner signs off a manual check.
- **Interim:** this answers OQ-13. Until the ledger exists, the runbook must carry a mandatory step: "list every erasure request since <archive date> and re-apply it before `systemctl start`".

**S1119-04 — Low — §11.19.7 step 9 (L177, L185–L188): `sshd -T` without `-C` does not evaluate `Match` blocks.**
- **Impact:** a `Match` block in an image drop-in (for example `Match User root` / `PasswordAuthentication yes`) passes the check but still applies.
- **Change:** after `E="$(sshd -T)"`, add:
  - `grep -Rqsi '^[[:space:]]*Match[[:space:]]' /etc/ssh/sshd_config /etc/ssh/sshd_config.d/ && { echo "sshd_match_block" >&2; exit 1; }`
- **Port check:** refuse if `sshd -T` prints more than one `port` line. Only the first port would be opened in ufw:
  - `[ "$(sshd -T | grep -c '^port ')" = 1 ] || { echo "sshd_multi_port" >&2; exit 1; }`

**S1119-05 — Low — §11.19.2 step 4 (L38, L40): the import gates run third-party package code as root.**
- **Evidence:** `import discord, … davey` executes package `__init__` code as root. A compromised wheel that matches the hash is out of scope, but there is no need to give it root at install time.
- **Change:** prefix both `/opt/employee/venv/bin/python -c …` lines with `runuser -u employee --`. Both only read files.

**S1119-06 — Low — `core/db/backup.py:67-76` (`backup_knowledge`) and `:166-169` (`__main__`): two gaps against the spec.**
- **(a) `.tmp-*` files are not excluded.** The main-thread note calls this a required follow-up.
  - Impact: in-flight `mkstemp(prefix=".tmp-")` files (store.py:166) are archived, including partial writes of `erase_user` output.
  - Change: in the loop, before `os.lstat`, add `if n in files and n.startswith(".tmp-"): continue`. In `test_knowledge_backup_roundtrip_and_skips_symlink`, seed `.tmp-x` and keep `files == ["a.md", "sub/b.md"]`.
  - I did not make this one-line fix: write access was denied in this audit.
- **(b) `restore-knowledge` accepts any file name in `backups/`, including `daily-*.db`.** It fails safely with `restore_failed`. Change: add `or not re.fullmatch(r"knowledge-\d{8}T\d{12}Z\.tar\.gz", sys.argv[2])` to the name check.

**S1119-07 — Medium — §11.19.10 "Secrets" (L371): rotation "when believed exposed" bounds nothing.**
- **Evidence:** a copied snapshot cannot be detected, and the backup retention is unknown (OQ-11).
- **Constraint:** within the owner decision (Hostinger weekly backups are the only off-host copy), the only control is to make old copies worthless and limit the damage. Replace the bullet with:
  - **Scheduled rotation:** rotate the three API secrets (Discord bot token, Anthropic, Google) at least every 90 days. Rotate immediately on any Hostinger security notice, any suspected Hostinger account or API-token compromise, any device loss, or a restore that needed support staff. Record the date in `setup.md`.
  - **Damage limits:** set a monthly spend cap on the Anthropic key. Restrict the Google key to the APIs it uses and set a quota. Give the Discord bot only the gateway intents and permissions it needs.
  - **Hostinger account:** it is root-equivalent (browser console, root password reset, backup restore and download). 2FA is mandatory.
  - **Hostinger API token:** use the least scope available, keep it only on the owner's machine (never on the VPS or in the repo), and revoke it when it is not in use.
  - **No other private keys on the VPS:** no wider-scope private keys (for example GitHub keys with write access) in any home dir. They would also be in the plaintext backup. A read-only deploy key is acceptable.

**S1119-08 — Medium — §11.19.10 erasure bound (L365): the privacy notice cannot state an unknown bound.**

Erased data can remain in those backups until they expire. We do not restore them except to recover from a failure, and after any such restore we re-apply all erasure and opt-out requests."
- The last sentence is true only once S1119-03 is done.
- After a Hostinger restore, run `python -m core.db.backup` (prune) and the retention sweep before `employee.service` starts, so restored copies past their bound are removed immediately.
