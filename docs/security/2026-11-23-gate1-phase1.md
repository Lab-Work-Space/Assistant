## Findings

### Core-first slice

**G1-01 — High — Budget fails open.**
- **Where:**
  - §3.0 `core/extensions.py`: "A missing module is skipped with a WARNING".
  - §3.0: "Until `core.budget.ext` runs, `ctx.budget = NoopBudgetGuard()`".
  - Plan TASK-025 deps (007, 010, 011, 012A, 013A) omit TASK-018, so the CLI harness can call paid providers with the Noop guard.
  - §3.11 gives no gate or record path for `image_generate`, TTS or STT spend. The STT worker has no DB access.
- **Required change:**
  1. Startup refuses, and the CLI refuses, when `ctx.budget` is `NoopBudgetGuard` and any real provider adapter is registered. Only tests may inject Noop.
  2. Add 018 to the TASK-025 deps.
  3. `level()` returns `stop` on a DB read error (fail closed). `record()` errors are logged and never drop silently.
  4. Image and TTS check `level()` before the call and record after it. The `voice_transcribe` result carries STT usage, and `on_done` records it.
  5. A stream aborted before its `usage` event (timeout, cancel, error) records an estimate: input tokens counted locally or by char/4, plus output chars streamed so far.
  6. Correct the §3.11 statement "Maximum overshoot of one call = AGENT_MAX_OUTPUT_TOKENS". The real overshoot is up to `AGENT_MAX_CONCURRENCY` × (input + output) of one call.

**G1-02 — Medium — Exact-value masking breaks on empty or short secrets.**
- **Where:**
  - §5.4: "exact values of `DISCORD_BOT_TOKEN` … and the password part of `DATABASE_URL`".
  - The whole-line check: "check the line again for each exact secret value".
- **Problem:**
  - CLI mode runs with the Discord token unset, and a passwordless `DATABASE_URL` yields an empty password. Then `"" in line` is always true: every log record becomes `log.masking_failure` (total log loss), and every masked prompt is refused.
  - A short or common password (for example `postgres`) masks normal words. §3.2 step 3 then refuses every prompt with `prompt_contains_secret`.
  - The whole-line check also misses a value whose JSON-escaped form differs from the raw form.
- **Required change:**
  1. Leave out of the exact set every unset value and every value shorter than 12 characters.
  2. `Config.load` refuses to start on a set secret shorter than 12 characters, except an empty DB password in CLI/dev mode, logged as WARNING.
  3. The line check searches for the raw form, the URL-encoded form and the `json.dumps(v)[1:-1]` form.
  4. Add key-name masking for any value type (global rule 14, backend rule 1): keys matching `token|secret|password|api_key|authorization|cookie`, including nested dicts and lists.
  5. Add regexes for `Bearer\s+\S+`, `x-api-key`/`x-goog-api-key` header lines and `ya29\.[\w-]+`.
  6. Add an idempotence test: `mask(mask(x)) == mask(x)`.

**G1-03 — Medium — Free text reaches logs, the DB and chat (global rule 16).**
- **Where:**
  - §3.4 step 5, "`tool_error` (masked message, stack trace logged)". jsonschema `ValidationError` text echoes argument values, which contradicts "Arguments are not logged".
  - §3.10, "`error=<type>: <masked msg>`". This goes to `jobs.error`, then to the voice status embed (§5.6).
  - §3.10, "stderr is capped at 64 KB, masked and logged" (ffmpeg or STT stderr can carry content).
  - `progress.msg` is not specified.
- **Required change:**
  1. `invalid_arguments` logs only the failing JSON path and validator keyword.
  2. Worker errors store `<ExceptionType>` plus a fixed code only. The message is written only when `LOG_LEVEL=DEBUG`, read from the process env.
  3. stderr is logged as a length and an sha256 only.
  4. `progress.msg` must match a fixed-vocabulary regex (`^[a-z_]{1,40}$`), otherwise it is dropped.
  5. The log masking test captures the emitted line, not the record object.

**G1-04 — Medium — `wrap_untrusted` gaps (§6.2, §3.2 step 5).**
- **Where:**
  - `_TAG = re.compile(r"<(/?)(untrusted|tool_result)"…)` misses `< /untrusted>`, `</ untrusted>` and fullwidth `＜/untrusted＞`.
  - §3.2: "wrapped as `<tool_result name=… ok=…>`" does not say the body is escaped. Knowledge bodies (64 KB) can contain `</tool_result>`.
  - `source` and `author_id` are interpolated without sanitising.
- **Required change:**
  1. Use `_TAG = re.compile(r"[<＜]\s*(/?)\s*(untrusted|tool_result)", re.I)`.
  2. Every `<tool_result>` body goes through the same escape. Build the tool_result through one helper in `untrusted.py`.
  3. `source` must match `^[a-z_]{1,32}$` and `author_id` must match `^[0-9]{0,20}$` (assert, else raise).
  4. Tier 2 truncates the text before wrapping, never after.
  5. Add tests for each variant, with a 200 KB input to bound the time.

**G1-05 — Medium — The T8 claim "no DB or Discord credentials" is false for same-uid children (global rule 4).**
- **Where:** §2 "do not get `DISCORD_BOT_TOKEN` or `DATABASE_URL`", §3.10 Spawn and §6.1 T8.
- **Problem:**
  - The worker runs under the bot's uid in the bot's container. On Linux it can read `/proc/<ppid>/environ`; on macOS it can read `KERN_PROCARGS2`. Either gives it all secrets.
  - In the local and CLI harness, `cwd=PROJECT_ROOT` also exposes `.env.local`.
  - The worker imports any module that matches the regex, so `selftest_*` runs even when `JOBS_ENABLE_SELFTEST=false`.
- **Required change, one of:**
  - (a) Run workers under a dedicated uid: `create_subprocess_exec(user=<jobs uid>)` in the container, with the bot's env and `.env.local` unreadable to that uid.
  - (b) Reword T8 and §2 to state the limit honestly ("no secrets passed; same-uid process can read the parent's environ; acceptable only while every kind is first-party and parses no untrusted file format"), and add that rule as a check for new kinds.

  In either case:
  - `worker_entry` imports only kinds named in an explicit allowlist passed in by the supervisor.
  - ffmpeg runs with a forced input format (`-f s16le -ar … -ac …`) and `-protocol_whitelist file`, with input and output paths only under `VOICE_TMP_DIR/<session>`.

**G1-06 — Medium — Approver identity in the CLI harness (plan TASK-025 `--as admin|user`; spec §3.5 is Discord-only; §5.1 is verbatim).**
- **Problem:** The spec defines no actor or approver abstraction, so the harness must either fork the approval logic or fake a Discord member. `--as admin` is an approval bypass if it can act on the real DB or on Discord-created rows.
- **Required change:**
  1. Add to §5.1 an `Actor{kind: discord|cli, user_id}` and an `ApproverPolicy.is_approver(actor)`. The approval service calls the policy, and `decided_by` stores `cli:<name>` for CLI decisions.
  2. The CLI policy is enabled only when the process env (never `.env.local`, global rule 7) has `EMP_CLI_DEV=1` AND `DISCORD_BOT_TOKEN` is unset.
  3. The CLI may decide only approvals it created (`requested_by` with the `cli:` origin).
  4. `/budget set` uses the same policy.
  5. Fix the env name mismatch: the plan says `DISCORD_TOKEN` and the spec says `DISCORD_BOT_TOKEN`.

**G1-07 — Medium — Stored prompt injection through `knowledge_write` (global rule 8).**
- **Where:** §3.4 `knowledge_write` (no human trigger, any seeded area) and §3.9.
- **Problem:** A run tainted by injected channel text can write into `rules` or `memory`. Later, untainted runs and other agents read that text as standing guidance. Wrapping reduces the risk but does not remove it.
- **Required change:**
  1. Agents may write only to `memory` and to a `notes`-style area. `rules` is read-only to tools and edited by humans only.
  2. Every entry's frontmatter records `author_agent`, `run_id`, `trigger` and `human_user_id`.
  3. `knowledge_write` is `needs_human_trigger=True`, or else allowed only in runs with a `human_user_id`.
  4. An empty slug, for example from a Thai-only title, falls back to `entry-<run_id[:8]>`.

**G1-08 — Medium — Secret distribution per container and the DB role (TASK-005, TASK-006; global rule 4).**
- **Where:** §2 "PostgreSQL runs in its own container" and §6.1 T2. No distribution rule is given.
- **Required change:**
  1. Compose gives no shared `env_file`. Postgres receives only `POSTGRES_*`, and the bot receives only its own variables.
  2. The Postgres port is not published, or is bound to `127.0.0.1` for the local harness only.
  3. The runtime DB role is not a superuser, owns no schema and is separate from the Alembic migration role. It gets no `TEMPORARY` and no `CREATE`.
  4. The bot runs non-root with a read-only root filesystem. Only `LOG_DIR`, `KNOWLEDGE_DIR` and the tmpfs are writable.
  5. Log files follow global rule 17 (O_NOFOLLOW, 0600 files, 0700 directories).
  6. `.dockerignore` and `.gitignore` use anchored patterns, and a test proves `.env.local` is excluded while sources stay (global rule 19).

**G1-09 — Low — CLI sink output (TASK-025).**
- **Required change:**
  1. `CliReplySink` runs `mask_secrets` on every string, like the Discord sinks.
  2. It strips C0/C1 and ESC control characters (terminal escape injection from model or tool text) before printing.
  3. `send_file` writes with `O_CREAT|O_EXCL|O_NOFOLLOW` and 0600, into a 0700 directory created by `mkdtemp`.
  4. The harness module is not imported by `core.__main__`.

### Discord slice

**G1-10 — High — Meeting transcripts readable by every guild member (§3.7 `on_done` step 3, §3.9, §6.1 T7/T11).**
- **Problem:**
  - A transcript of a private voice channel goes to the global `meetings` area. Any member can reach it through any agent with `knowledge_*` (or `*`) tools, using `knowledge_read`, or hook lines through `knowledge_search`.
  - Notes have no retention, and an opt-out after the session does not remove a person's lines.
  - Notes live in the repo tree (`knowledge/meetings/`) and can be committed to git.
- **Required change:**
  1. TASK-014 (core-first) stores `visibility` frontmatter (`public` | `members:<ids>`) and the read tools enforce it. A `members:` entry is readable only when `ctx.human_user_id` is in the list or holds the approver role, and never in runs with `human_user_id=None`. The index line for such an entry exposes no hook text.
  2. Voice notes are written `members:<participants>` unless the voice channel is viewable by @everyone.
  3. Define a retention period for `meetings` (suggest 90 days) and add it to the sweeper.
  4. Add an erasure procedure: an approver-run command deletes a user's lines or a whole note.
  5. Add `knowledge/meetings/*` (except `_index.md`, or the whole area) to `.gitignore`.
  6. `tasks` (which holds human `description` text) also needs a retention row in §5.3.

**G1-11 — High — Side effects on people without a human trigger or a permission check (§3.4 `respond`, `pull_user`; §3.8; §6.1 T1).**
- **Where:**
  - `respond target {thread|dm, id}` lets any injected run post persona text into any channel or thread the bot can write to, including the approval channel and channels the attacker cannot post in. This allows cross-channel exfiltration of private-channel context.
  - `respond` can also DM any member, at 5/h per target.
  - `pull_user` `here`/`dm_invite`/`thread_invite` needs no human trigger. `thread.add_user` can add a target to a private thread.
- **Required change:**
  1. In runs with `human_user_id=None`, `respond` is limited to the run's own channel or thread.
  2. In human runs, a `thread`/`here` target must be a channel the triggering human can view and send messages in, and never `APPROVAL_CHANNEL_ID` or `ADMIN_NOTIFY_CHANNEL_ID`.
  3. A DM target other than the triggering human requires `needs_human_trigger`.
  4. `pull_user` is `needs_human_trigger=True` for all destinations, and `thread_invite` requires the human to be able to view the thread.
  5. Every target id must resolve inside `DISCORD_GUILD_ID`.

**G1-12 — Medium — Voice notice, consent races and deletion guards (§3.7, §5.5, §5.7).**
- **Required change:**
  1. Post the notice in the voice channel's own text chat, not only the command channel. A present member whose delivery is `channel` but who cannot view that channel gets a DM, and is excluded if the DM fails.
  2. The notice text discloses processing by Google STT and LLM, who can read the note (G1-10), and the transcript retention.
  3. Opt-out race: hold a per-session lock shared by the sink write and the opt-out delete. Build the job `files` list from the current `allowed` minus `voice_optouts` at stop time, and have the worker skip any user in the payload's `excluded` list.
  4. Drop packets whose `user` is None or unresolved.
  5. Every delete (opt-out, worker `finally`, `on_done`, startup purge) checks that `realpath` is under `realpath(VOICE_TMP_DIR)/<session>` and that the path is not a symlink (global rules 17, 20).
  6. `Config.load` refuses a `VOICE_TMP_DIR` that is not absolute, is `/`, is inside `PROJECT_ROOT` or `KNOWLEDGE_DIR`, or is a symlink. The directory is created as 0700 and owned by the euid.
  7. Restart recovery and failure paths also clear the `voice_transcribe` job `payload` and `result` (display names, paths).

**G1-13 — Low — Webhook persona and Discord-specific masking (§3.3 WebhookSink, §5.4).**
- **Required change:**
  1. Reuse an existing `emp-personas` webhook only if `webhook.user.id == bot.user.id` (created by the bot). Otherwise create a new one. A pre-created webhook could be controlled by any member with Manage Webhooks.
  2. Add every cached webhook token to the exact-value mask set.
  3. Add the host-less regex `/webhooks/\d+/[\w-]{60,}`.
  4. Set the `discord` and `aiohttp` loggers explicitly to WARNING, so gateway payloads stay out of the logs.
  5. Check the DM membership gate with `guild.get_member` or `fetch_member` at each message, never a cache of the result.

**G1-14 — Low — Approval UX hardening (§3.5, §5.5).**
- **Required change:**
  1. Refuse an approver role id equal to the guild id (@everyone) or a managed role.
  2. The approval embed shows the origin channel, the triggering human (or "agent-initiated") and the text "generic approval: informational, grants no permission".
  3. Phase-2 handlers must act on DB state only, never on agent text that claims an approval happened.
  4. `/budget set` checks the role server-side by fetching the member, never by Discord command permissions alone.

### G1-05 option (b)
Option (b) is acceptable for phase 1 with RC-4, because the only kinds are first-party (selftest, and `voice_transcribe` in Slice B).

Option (a), a dedicated worker uid with the bot env, `.env.local`, `LOG_DIR` and `KNOWLEDGE_DIR` unreadable to it, becomes mandatory before merge of any job kind that does one of these:
- decodes a user-supplied container, codec or attachment (Ogg/Opus demux moved into a worker, uploads, images, PDFs) or fetches URLs;
- runs third-party or agent-chosen code, such as the phase-2 launcher or `destructive_cmd`/`file_write_outside` handlers that spawn jobs.

Recommendation (not blocking): replace the PR checklist item with a test asserting that the registered kind set equals a reviewed list (global rule 6). On Linux, `prctl(PR_SET_DUMPABLE, 0)` in the bot makes `/proc/<ppid>/environ` unreadable to same-uid workers, which is cheap defence in depth.
