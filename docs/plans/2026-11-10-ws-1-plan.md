# WS-1 plan

Spec section map: 1 (goal, evidence) -> WS-S1, WS-T2; 2.1 workspaces -> WS-BE1; 2.2 file tools -> WS-BE1; 2.3 `ws_run` -> WS-BE2; 2.4 export -> WS-BE2; 2.5 grants and prompt -> WS-P1 (guide text), WS-BE3; 3 controls -> WS-BE3 (`ws.enabled`, caps), halt in every build task; 4 errors -> every build task (AC) and WS-T1; 5 tests -> inside each build task, integration in WS-T1, acceptance in WS-T2; 6 residual risks R1-R5 -> WS-S1, WS-S2. Extra: probe pin alert -> WS-BE4.

Conventions: TypeScript, vitest (`npm test`), DB tests via `npm run test:int` (Postgres 127.0.0.1:54329). Every refusal is a fixed text. Logs and audit never carry file content. Gate 1 conditions bind every task. `ws.enabled` defaults to `false` until Gate 2 passes. Reuse dev-job sandbox pieces: `docker-compose.devjob.yml` (prep network, registry proxy), `devjob/launcher.ts` (container spawn), `devjob/registryproxy.ts`. Code refuses non-software actors in every `ws_*` tool.

## Build tasks

Three sequential backend dispatches for WS-1 (BE1 then BE2 then BE3), each committed before the next; never parallel in one worktree. WS-BE4 is a small independent fourth dispatch (separate files, may run before WS-S1 since it is not part of the workspace feature). WS-P1 (ai-prompt) touches only its own file.

## Dependency order and parallel groups

1. WS-S0
2. Parallel: WS-S1, WS-DOC1
3. WS-P1 (after S1)
4. Backend dispatch 1: WS-BE1
5. Backend dispatch 2: WS-BE2
6. Backend dispatch 3: WS-BE3
7. Backend dispatch 4: WS-BE4 (may be pulled forward to run right now, before WS-S0, because it is independent; never concurrent with another backend dispatch)
8. In sequence: WS-T1, WS-T2, WS-S2, WS-DEP, WS-DOC2, WS-R

File-contention notes: BE1 touches migrations, a new workspace module, the tool registry and the `/ws` command; BE2 touches a new `ws_run` module and reads `devjob/launcher.ts` and `devjob/registryproxy.ts` (reuse by import; avoid editing them, and if an edit is needed, re-run dev-job tests); BE3 touches the department grant config, the software head prompt and config keys; BE4 touches `guard.ts`/`app.ts` boot path. BE3 and BE4 both may touch `app.ts`, so keep them sequential.

## Risks

- Deadline: CTO task due 2026-11-17; the critical path is S0, S1, P1, BE1-3, T1, T2, S2. Consider running WS-BE4 first since it is small and addresses a live outage.
- R1-R5 from the spec stay open by design; R5 (no real Chrome test) means F1-F5 is verified by mock tests only.
- Docker is required for WS-T2; if Docker is unavailable on the owner Mac, WS-T2 is Blocked and returns to the owner.
- WS-BE4 alert is only possible after Discord is ready; with no Discord the alert is lost (boot log still carries the reason).
