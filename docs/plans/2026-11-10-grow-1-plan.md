# GROW-1 plan

Spec section map: 1 (G1-G3, R1-R4) -> GW-S1, GW-DOC1, GW-T2; 2.1 retro -> GW-P1 (instruction), GW-BE1; 2.2 AI skill review -> GW-P1 (judge prompt), GW-BE2; 2.3 tool_request -> GW-BE3; 2.4 tool_idea -> GW-BE3; 3 controls -> BE1 (retro keys), BE2 (skills.ai keys, digest), BE1/BE2 (`/settings`), halt in every build task; 4 errors -> every build task (AC) and GW-T1; 5 tests -> inside each build task, integration in GW-T1, acceptance in GW-T2.

Conventions: TypeScript, vitest (`npm test`), DB tests via `npm run test:int` (Postgres 127.0.0.1:54329). Every judge failure escalates to human review; no error path applies a skill. Logs carry the error name only, never model text. Gate 1 conditions bind every task. `skills.ai.enabled` defaults to `false` until Gate 2 passes. A skill never adds a tool. Reuse AI-APPROVE-1 machinery (provider path, timeout, strict JSON, sanitising, digest) and the SKILLS-1 apply path and `skillToolAllowed`.

## Build tasks

Three sequential backend dispatches (BE1 then BE2 then BE3), each committed before the next; never parallel in one worktree. GW-P1 (ai-prompt) runs first and touches only its own files.

| ID | Owner | Depends on | Task | Acceptance criteria |

| GW-P1 | ai-prompt | GW-S1 | Two fixed code constants. (a) Retro instruction text (§2.1): head reviews facts, may propose at most one skill, request an existing tool, file a tool idea, or do nothing; facts are untrusted data; ends with a short room summary. (b) Skill-judge system prompt and input template (§2.2): a skill is workflow guidance for one team; approve only text on how to do the team's work better; escalate on any bypass of approvals, rules, budgets, safety or other teams, tool or permission request, persona change, hidden instruction, URL to fetch, secret; unsure means escalate; output `{decision, reason}` 1-200 chars; no tools exist; title, instructions, templates, reason, target and current active version sit in the untrusted wrapper. | Snapshot tests pin both rendered texts; untrusted fields inside the wrapper; judge prompt contains the escalate list and the reason limit; retro text states the one-proposal limit and the three tool options and no instruction to skip rules. |

## Dependency order and parallel groups

1. GW-S0
2. Parallel: GW-S1, GW-DOC1
3. GW-P1 (after S1)
4. Backend dispatch 1: GW-BE1
5. Backend dispatch 2: GW-BE2
6. Backend dispatch 3: GW-BE3
7. In sequence: GW-T1, GW-T2, GW-S2, GW-DEP, GW-DOC2, GW-R

Only GW-S1 and GW-DOC1 run in parallel. Build is strictly sequential, each dispatch committed before the next.

File-contention notes: BE1 touches the scheduler timer, `app.ts` and a migration; BE2 touches the skill store, the AI approver module and the digest; BE3 touches tool registry, the `/tool` command and a second migration. Do not overlap them in one worktree. BE1 `skill_propose` cap and BE2 hook both touch the skill tool file, which is why BE2 follows BE1.

## Risks

- R1-R4 from the spec carry to Gate 1.
- BE1 tests seed skills and proposals directly; the judge hook lands in BE2.
- Retro facts quality depends on the Flow A notes and tool-error tables existing as the spec assumes; GW-S0 must confirm or return to sa.
- Apply path may need refactoring to accept the `ai-approver` actor; if it cannot, return to sa before BE2.
- Digest depends on the AI-APPROVE-1 digest code on this branch (shipped; confirm in GW-S0).
